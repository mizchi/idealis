# 0098: 文法の候補を、意味と結果が読み取れるかで評価するループ

mizchiの方針: 文法を設計しながら、その文法で書いたモデルの意味や検査の結果を読み手が読み取れるかで評価する。文法はまだ確定せず、意味論を優先する。最初の候補はQuint風。読み手は文脈を持たない新しいsubagent。

## 仕組み

- **正解**: [0097](0097-rmodel-reference.md)の参照評価器。モデルごとに、各checkの判定（成り立つ・破れる・到達できる・到達できない・空）と、各actionが到達できるある状態で実行できるか、を出す。
- **候補の文法**: 核のモデル（今はrmodelの構文木）をテキストに出力するprinterだけを作る。parserは採用した文法にだけ書く。v0のQuint風:
  - `module M { ... }`、sortは`type User`、enumは`type E = A | B`。
  - 静的な関係は`const`、変わる関係は`var`。型は`Set[T]`（集合）と`A -> Set[B]`（二項関係）。多重度は型の後ろの注記（`// each A has at most one B`）。
  - 集合の演算はメソッド（`a.union(b)`・`a.exclude(b)`・`a.intersect(b)`・`a.subseteq(b)`・`s.contains(x)`・`s.size()`）、量化は`S.forall(x => ...)`・`S.exists(x => ...)`、関係は`r.image(s)`・`r.preimage(s)`・`r.compose(t)`・`tuples(a, b)`。
  - actionは`action name(x: T) = all { 条件, v' = 式 }`。代入しないvarは変わらない（Quintと違う点で、読み取れるかを測る）。
  - 性質は`invariant Name = 式`・`reachable Name = 式`。scopeは`check { User = 2, steps = 6 }`。
- **問い**（正解は参照評価器から自動で作る）:
  - 性質: 各checkについて「成り立つ／破れる／空（初期状態がない）」または「到達できる／到達できない／空」。
  - action: 各actionについて「ある到達できる状態で実行できるか（はい／いいえ）」。
- **読み手**: 文脈を持たないsubagent（haiku）。道具を使わず、文法の説明を渡さずに、モデルのテキストと問いだけを渡す。答えはJSON。5モデルを1体に読ませ、1回の評価で2体。
- **採点**: 問いの種類ごとの正答率と、誤答の内容。

## 正しさ（結果を見る前に固定）

- dev: 生成したモデルのseed 300〜のうち、空でない最初の10モデル。確認: seed 2000〜のうち、空でない最初の10モデル。確認は、devで文法を変えた後に1回だけ使う。
- 判断: v0の正答率を記録する。v1以降の変更は、devで誤答を読んで仮説を立て、確認で正答率が上がり、どの問いの種類でも下がらないときに採用する。
- 正答率の数値だけで判断しない。誤答は1件ずつ読み、文法の読み違い・問いの曖昧さ・読み手の推論の誤りに分ける。問いの曖昧さによる誤答は、その問いを直した後にdevでやり直し、確認には持ち込まない。
- 読み手の答えは、promptと一緒に記録する。

## 範囲外

- 型・多重度の違反を報告する意味（0099）。
- 検査の結果の表示の評価（次の段階で、同じ仕組みに問いを足す）。
- parserの実装。
