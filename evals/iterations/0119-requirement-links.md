# 0119 自然文と遷移の対応を追う

ProR は要求文と Event-B の要素を参照で結び、どちらかが編集されたらリンクを再確認する。透析装置の事例では、要求の種類に応じて不変条件の証明、時相検査、挙動のアニメーションを使った。Octys の安全性分析では、サブシステムごとの前提と責務を仕様に戻って特定している。発送の試作では、適用範囲・要求の節・対応する性質を明示する形にした。 [ProR 統合仕様](https://wiki.event-b.org/images/Pror-integration.pdf) · [透析装置](https://doi.org/10.1016/j.scico.2017.11.002) · [Octys](https://doi.org/10.1007/978-3-319-68499-4_10) · [要件から Event-B への追跡](https://doi.org/10.1016/j.scico.2015.06.002)

## 発送で試した三案

| 案  | 要件と式の結び方                                                                                                       |
| --- | ---------------------------------------------------------------------------------------------------------------------- |
| A   | `SHIPMENT-TRACKING → ShippedStays` と性質全体の検査結果を表示する。                                                    |
| B   | 要件全体の文と式を一組としてレビュー時点の版を保存する。                                                               |
| C   | 発送済みを保つ節と追跡方法を保つ節に分け、各節の文・式・モデル検査・レビューを同じ行に置く。適用範囲を両節で共有する。 |

C の試作表示を文法にした場合の記法案。

```text
requirement SHIPMENT-TRACKING
  applies "発送済みの注文に対する、実行可能な各操作の直後"
  status   "発送済みのまま"       -> ShippedStays.status
  tracking "追跡方法は前後で同じ" -> ShippedStays.tracking
```

rmodel の参照評価器で同じ発送モデルを検査した。C の二式は、このモデルの `ShippedStays` から取り出した。追跡方法を比較できる範囲は、前後とも発送済みの場合。発送済みを抜ける遷移の検出は状態の節が担う。対応レビューの版は文と式の正規化 IR から、モデル検査の版はモデル全体の正規化 IR から計算した。節の切り出しは発送の式の形に依存する。 [事前計画](../plans/0119-requirement-links.md) · [全7対照の結果](../runs/0119-requirement-links/comparison.json)

| 変更                                           | rmodel の判定とリンク                                      | B の対応レビュー       | C の対応レビュー                           |
| ---------------------------------------------- | ---------------------------------------------------------- | ---------------------- | ------------------------------------------ |
| 言い換え、または「確認時に変更してよい」に変更 | リンクは解決し、既存の式は成立                             | 要件全体を再確認       | 追跡方法の節だけ再確認                     |
| 式から追跡方法の条件を削除                     | 名前は解決し、残った式は成立                               | 要件全体を再確認       | 追跡方法の節の参照先がなく、検査も判定なし |
| 確認操作で追跡方法を Post に上書き             | 旧モデルの検査結果は失効し、現行モデルは最短2操作で違反    | 文と式のレビューは現行 | 文と式のレビューは現行。追跡方法の節が違反 |
| 性質名の変更、モデルコメントだけの編集         | 名前の変更はリンク切れ。コメントは判定とレビューに影響なし | 同左                   | 同左                                       |

## 独立した読み手の観察

代理読み手3人に、案と変更の組み合わせを変えて提示した。全員が三案を見て、三つの変更は一人につき一度ずつ読んだ。全員が C を最も調べやすいと選んだ。Q1〜3 ではリンク、式の判定、対応レビューを区別できた。初見で二人が「現在のモデル検査　成立」を要件全体の成立と読みかけたことも記録した。一人は「追跡方法の節に判定がないことをすぐ確認できた」と答えた。この結果は発送1例と代理読み手3人に限る。 [回答1](../runs/0119-requirement-links/answer-1.md) · [回答2](../runs/0119-requirement-links/answer-2.md) · [回答3](../runs/0119-requirement-links/answer-3.md)

次に試す表示は、全体の成立を先頭に置く形から、未対応の節と再確認の範囲を先に示す形に変える。データモデルは、一節の短い要件をそのまま表せて、複数節があるときに節ごとの根拠へ進める形を候補とする。要件の日本語と式が一致するかはレビューの判断であり、言い換えと意味が変わる編集が同じ状態になることを実行でも確認した。

## Event-B Agent と、修正で振る舞いが消える対照

Wang らは自然言語から refinement を計画し、Event-B を生成する。ProB の反例と Rodin の証明義務を使い、モデル・証明を反復修正する。27システムで証明義務の解消率97.86%、要件カバレッジ97.13%、論文の定義による要件充足率93.79%を報告した。refinement 固有の解消率は92.56%。要件指標は生成モデルに付けた要件 ID と関連する証明義務を使い、抽象段階で成立した要件は具体化の後も引き継がれるという仮定で集計する。論文は要件の不整合への対応を今後の課題とし、ID の形式を手で補正したと記録している。表6の全体平均は74.45分。 [Event-B Agent §§4.4, 5.1–5.4, 7](https://arxiv.org/html/2605.17475v1)

rmodel に取り込む価値があるのは、反例、証明義務、有限の修正操作を循環させ、モデルを変えたら過去の証明を再検査する設計。ガード強化や公理追加で対象の証明が通った場合も、元の業務要件の範囲をレビューする必要がある。論文 §5.5 のガード強化例は、含意の前件が成り立たなくなることで保存義務を閉じる。発送では、同じ形のガード変更で業務に必要な操作が消えるかを試した。 [修正演算と例](https://arxiv.org/html/2605.17475v1#S5.SS5)

| 発送モデル           | ShippedStays | Courier で確認済みに到達 | Post で確認済みに到達 |
| -------------------- | ------------ | ------------------------ | --------------------- |
| 正常                 | 成立         | 到達                     | 到達                  |
| 確認で Post に上書き | 違反         | 不達                     | 到達                  |
| 確認をすべて止める   | 成立         | 不達                     | 不達                  |
| Post だけ確認を許す  | 成立         | 不達                     | 到達                  |
| 上書きだけを除く     | 成立         | 到達                     | 到達                  |

追試では、要件側で Courier と Post の確認に到達できることを固定したため、振る舞いを縮める二つの案を区別できた。確認できる場所への到達を調べた結果であり、すべての発送がいつか確認されるという活性は別の問いになる。追試の範囲は、論文の修正操作を模した発送の固定モデルと人工故障に限る。 [追試の計画](../plans/0119b-repair-controls.md) · [結果](../runs/0119-requirement-links/repair.json)

`just requirement-links .artifacts/requirement-links-new` で新規ディレクトリに二つの結果 JSON と読み手用の画面を再生成できる。
