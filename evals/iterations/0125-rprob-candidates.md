# 0125 rprob の候補列挙

`rprob` を、rmodel の有限集合と二項関係を対象にする ProB 由来のアイデアを使った試作として明記した。全候補を準備時に保存する実装は、予算が小さくても候補数に比例してメモリを使い、関数を作るときは制約に反する関係まで作っていた。候補256個までは全体表を保持する。全体表に格納する値は1領域当たり最大2 KiB。大きな単項集合は必要時に復元する。二項関係は行ごとの選択表から復元し、`one` / `lone` は最初から各行の合法な値だけを含める。 [事前計画](../plans/0125-rprob-candidates.md) · [対応範囲](../../crates/rprob/SUPPORT.md)

| 負荷                               | 壁時計 ms（前 → 後） | 命令数 百万（前 → 後） | ピーク RSS MiB（前 → 後） |
| ---------------------------------- | -------------------: | ---------------------: | ------------------------: |
| 20 atom の集合4個、予算1、都度準備 |         23.09 → 1.32 |         573.66 → 13.80 |              36.11 → 1.92 |
| 4×4 全関数、候補走査20回、都度準備 |          6.63 → 1.49 |         160.10 → 18.93 |               2.38 → 2.41 |
| 4×4 の密な辺探索3回、準備再利用    |      133.58 → 131.30 |      2909.25 → 2832.01 |               9.46 → 8.92 |
| 権限モデル20回、準備再利用         |        72.60 → 72.21 |      1660.17 → 1672.06 |               2.26 → 2.27 |

表は1プロセス当たりの5標本の平均。macOS arm64、Hyperfine 2.0.0、同じ release ハーネスの変更前後を使った。都度準備で命令数が大きく減った。権限モデルでは壁時計が近く、命令数は0.7%増えた。大きな集合の変更前の初回標本は他より遅く、標本の幅は22.1–25.9 msだった。集約値と全標本、入力、判定、バイナリの SHA-256 を保存した。 [測定記録](../runs/0125-rprob-candidates/) · [測定コード](../experiments/rprob/candidates.py)

測定前に判定全文が一致することを確認した。集合4個の負荷は両版とも `Unknown`、密な辺モデルは両版とも最短16操作で全ての辺に到達した。参照評価器との既存の差分テストでは、予算切れと空の区別、最短深さ、宣言違反、操作到達が一致した。物理ビット順と宣言順が違う二項関係でも、4種類の多重度ごとに従来の列挙順と一致する。新たに扱える6×6全関数では、合法な初期候補が6⁶個あり、予算46,657では `Unknown`、46,658では完了し深さ0の到達を返した。 [差分・予算テスト](../../crates/rprob/tests/reference.rs) · [列挙順テスト](../../crates/rprob/src/bits.rs)

`just rprob-candidate-bench <新しい出力先> <変更前のreleaseバイナリ>` で比較を再実行できる。今回の変更前バイナリは作業ツリーから差分適用前に作り、`.artifacts/0125/rprob-before` に置いた。Git の HEAD は作業ツリーを識別するための参考情報。今回の測定で削減したのは主に候補領域の準備費用で、初期候補が多いモデルでは合法な候補も引き続き走査する。二項モデルの全体8 atom制限と、`set` / `some` の20 tuple制限が残る。
