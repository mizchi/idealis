# 0120: 引数を受け渡すだけの転送を loop でたどり、評価の再帰の段に積まない

[#127](https://github.com/mizchi/idealis/issues/127)を扱う。[plan](../plans/0120-forwarding-depth.md)（r5）を b57c0a376（origin/main、[#125](https://github.com/mizchi/idealis/pull/125) の merge）を基準に記録し、実装は stage I で `crates/rtlc/src/safety_expressions.rs` と `safety_lazy.rs`（`Snapshot` の field）だけを変えた。この文書は評価の段の記録で、`evals/runs/0120-audit/` に出力と sha256 を残した。push と remote merge は含めない。

変えた意味は 1 点で、引数が `Parameter` / `Capture` だけの転送を、段ごとの再帰ではなく 1 つの loop（`evaluate_forwarded`、`#[inline(never)]`）でたどり、hop を評価の再帰の段（`evaluation_depth`）ではなく転送の段（`forwarded`）に積む。再帰しない経路の 256 は評価の再帰の段だけと比べ、再帰する定義に入った経路の 128・葉の検査・ENABLED の subscript の見積もり・遅延関数の snapshot は合計（before の深さと同じ値）と比べる。hop ごとの `consume(1)` と判定は今と同じ位置と順序に残した。IR・wire・両 frontend・v1・要求の `bounds`・上限の値は変えていない。`size_of::<EvalContext>()` は before・after とも 72 byte（stage I の記録）。

## 判断

plan の採用条件を 1 つずつ照らした結果、性能の条件と、既存入力の完全応答のバイト一致の一部を除いて満たした。性能は plan が書く手順（測定を 1 つずつ流し、10% 以上の後退が出たら同条件の ABBA で再確認する）で共有の host の観測として流し、14 関数の比は 0.985〜1.051 で 10% 以上は 0 件だった。負荷のない host での測定は流していない（下の表）。product の挙動は、観測用の複製・固定 TLC・テストの期待値と食い違わなかった。評価の後に対照を足して F5c（と F5d）を満たした（correction-0003・0004）。最終レビューの Evidence の指摘を受けて、観測用の複製が公開する応答を product の直列化に直し、`published256` の枝（138 セル）を byte 単位で比べ直した（138 / 138 が同じ）。IR は compile の応答の `program` の raw の text も比べた。既存入力の完全応答のバイト一致（plan の条件）は、compile-tla と check-safety で測った（492 件の digest）。corpus の `check-tla` と `temporal-parity` は値の比較だけで、この 2 つのバイト一致は未測定である（`temporal-parity` の記録には応答の byte の集計の件数があるが、要求ごとの digest がなく、保存した記録から再計算できないので測定に数えない）。`just mutation` も流した。未測定が残るのは、既存入力のうち corpus の `check-tla` と `temporal-parity` のバイト一致（plan の条件）、採否の条件に含めない「手元のモデル」と、負荷のない host での Criterion（plan の条件ではなく、評価者が残した未測定）である。採否の最終判断は呼び出し側に残す。

## 観測用の複製

0119 の複製と同じく、評価の外では使わない。patch は [oracle-0120.patch](../experiments/call-depth/oracle-0120.patch)（`0120-oracle`: b57c0a376 の再帰しない経路の上限を 4,096 にし、再帰の 128 を残す）と [oracle-0120-after.patch](../experiments/call-depth/oracle-0120-after.patch)（`0120-oracle-after`: after に同じ変更。`descend` の本文が違うので patch は 2 つになった）で、どちらも `crates/rtlc/src` と `crates/idealis-core/src` だけを変える。sha256 は [checks](../runs/0120-audit/checks/) にある。

- probe は要求ごとに初期化し（core の `dispatch_observed`）、判定の前に `peakDepth`（256 と比べた値）・`peakTotal`（128 と比べた値）を記録し、product なら 256 の拒否を返す判定を `hits256` に数える。v1 の早い return と再帰の 128 が先に働く判定は数えない。応答には `probe` の field を、serialize した bytes に差し込む（key の順を変えない）。
- `published256` は、逐次の検査では最初の hit の出力（その位置を囲む fold のうち `replacement` が `Some` の最も内側の診断か、生の拒否）、並列の検査では各 worker の event の列を最初の hit で切って集約器の公開の順に当てた結果である。並列は、hit があった要求を 2 回目に、切った列を使って流し直して求める。 公開する応答は product の直列化（`Message` の serde）で書くので、key の順は応答と同じ（`kind`・`code`・`message`）で、応答の text のまま probe の member に入れる。
- 自己検査（`published256` が before の実際の応答と一致する）: 4 経路の v2 の 1,202 セル（own 1,110・published 92）、rtlc の unit test の `check()` 72 呼び出し（fold の診断 6 件を含む）、並列の 6 セルで、不一致 0（[paths](../runs/0120-audit/paths/analysis.txt)、[faults/pub-compare.txt](../runs/0120-audit/faults/pub-compare.txt)、[parallel](../runs/0120-audit/parallel/summary.txt)）。after 側も同じ（4 経路 1,202 セル、unit test 72 呼び出しの fold の診断 4 件）。 最終レビュー後に probe を直した版では、`idealis-core` の process を使わず cargo の test で 340 入力（Rust の frontend、IR v2）を流し、`published256` が実際の応答と byte 単位で一致することも確かめた: `oracle` と before が 27 / 27、`oracle-after` と after が 13 / 13（[published-inprocess](../runs/0120-audit/paths/published-inprocess.txt)）。
- probe の要求ごとの初期化: `hop-invariant-168`（深さ 510）の次に `hop-invariant-40` を同じ native process に流すと、40 の記録は 125 で、510 は残らなかった。

## 4 経路と before / after

410 入力（0074 の 265、0075 の 81、0119 の 28 と Quint の 4、0120 の新しい入力 32。重なりを除く）を、v1 / v2 と 4 経路（TS から Wasm、TS から native、Rust の Wasm、Rust の native）で、before・after・2 つの複製に流した。各 3,280 セル。比較は正規化しない応答（エラーの `code` と文言、違反の trace の全状態を含む）の sha256 で行った（[paths](../runs/0120-audit/paths/analysis.txt)）。

- IR の sha256 が before と after で異なるセルは 0。TS と Rust の正規化した IR は、両方が compile できる 772 セルで一致した。
- v1 の raw の応答が before と異なるセル（after・2 つの複製）は 0。
- v2 で check の応答を返したセルは 1,202。複製（before）の hit が 0 のセルが 1,110、1 以上のセルが 92。残りの 438 は compile の拒否（TS の `%`・`\div`・EXTENDS・RECURSIVE と frontend の上限）。
- **hit が 0 の 1,110 セルで、after の raw の応答は before と byte 単位で同じ。** 複製（before）の raw の応答も同じ。
- **hit が 1 以上の 92 セルのうち 46 セルで、after の応答が変わった**（complete 40、違反 4、`Integer division by zero` 2）。残る 46 セルは after も 256 で拒否し、同じ文言のまま。変わった 46 セルはすべて `0120-oracle-after` の hit が 0 で、after の raw の応答は複製自身の応答と一致した。拒否のままの 46 セルの after の応答は `published256` と一致した。
- 既存の 374 入力（Quint を除く）で変わったのは 12 セルだけで、予測と同じ: hop-84・hop-85 の Rust の native と Wasm（4 セル）と、hop-invariant-84・hop-invariant-85 の 4 経路（8 セル）。変わった先は複製の出力と同じ。新しい入力で変わった 34 セル: hop-124・hop-125 の Rust 2 経路、hop-invariant-124 の 4 経路、let-hop-83・set-hop-249・function-hop-246・record-hop-248・primed-hop-248 の各 4 経路、violation-120 の 4 経路、division-by-zero-120 の Rust 2 経路。
- 2 つの複製の raw の応答が一致しないセルは 0、`peakTotal` が一致しないセルは 0、`peakDepth > peakTotal` のセルは 0、after の `hits256` が before の `hits256` を超えるセルは 0。`peakDepth = peakTotal` のセルで hit か `peakDepth` が複製と異なるものは 0（`peakDepth < peakTotal` は転送を含む 172 セル）。
- fold の診断になるセルの数は 0（予測どおり。fold の診断は rtlc の unit test の 6 + 4 呼び出しで確かめた）。
- after の応答が fixture の期待値と一致しない入力は 0。fixture の期待値を複製の出力（hit 0 は before、hit 1 以上で after が拒否しないものは `0120-oracle` の出力、拒否するものは `0120-oracle-after` の `published256`）から導いた値と比べても、差は 0（1,194 セル: 1,102・46・46）。**複製の値が frozen の期待値と異なる点は見つからなかった。**

- 再帰する定義に入った経路は、深さ 128（転送を含めた合計）で `bounded / evaluation` になる。TLC が complete にする 3 入力は未確定のまま。before が 256 で拒否していた入力の一部が、after で `bounded / evaluation` になる（例 A）。
- 256 と比べる値が 256 以上の入力は型付きで拒否する。`Update` と `At` の spine と、根が `Prime` の引数は段ごとに数える。`UNCHANGED V8` は 256 の拒否のまま。
- stack の最小は、転送を含む種類で before より大きくなる種類がある（forward-set 250 の debug は 2,372 KiB）。debug の build を 2 MiB の thread で動かす利用者は、深さ 250 近くで abort しうる（要件は 8 MiB）。
- CLI の Wasm は v1 しか出さないので、v2 の上限は測れない。

## plan からの逸脱

- **文書の変更範囲。** plan は `crates/rtla-compiler/README.md`・`crates/rtla-compiler/SUPPORT.md`・`docs/rust-frontend.md` を「数（256、128）は変わらないので変えない」とした。実際には 3 つとも 1 行を変えた。転送は 128 には数えるが 256 には数えない、という数え方の規則を述べる生きた文書だからで、数は変わらなくても規則は変わった。変更は正確なので残す。
- **観測用の複製の patch が 2 つ**（下の「評価で見つけた点」の 4）。
- **対照の追加**（correction-0003・0004）。plan の「期待値が変わる既存のテスト」の範囲外で、test 1 件と helper 1 件を足した。製品の source は変えていない。
- **plan のファイル一覧にない変更（byte の比較のため）。** `evals/experiments/usable/native.ts` に `requestText`（応答の行を parse せずに返す）を足した。4 経路・corpus・temporal-parity で応答を byte 単位で比べるのに必要で、既存の `request` の挙動は変えていない。同じ理由で `evals/experiments/usable/wasm-text.ts`（Wasm の応答の text を返す）、`evals/experiments/p0-checker/corpus.ts`（測定の外で、応答の byte の sha256 を record に足す）、`evals/experiments/evaluator-tuning/corpus-summary.ts`（その sha256 を比べる。足していない古い run の集計は変わらない）、`evals/experiments/temporal-tuning/parity.ts`（応答の byte の sha256 を before の Wasm と比べる）を変えた。測るものは変えていない。
- **`analyze-tlc-0120.ts` の判定を `tlc-judge-0120.ts` に切り出した。** 予期しない error・TLC が違反か 0 除算に達する入力での after の 256 の拒否や `bounded` を不一致に数える。TLC が complete の入力では、`oracle-after` の hit が 0 のセルで after が `bounded / work`・256 の拒否・before にない compile の拒否を返したら不一致に数える（`hop-invariant-124` の after の結果を差し替えると不一致になる）。`--self-test` は欠陥のある入力 20 件を流す。
- **Criterion は共有の host（load 2.6〜3.9）で流した。** plan が書くのは直列の測定と 10% 以上での ABBA の再確認で、どちらも満たした。負荷のない host での測定は流していない。
- **`evaluator-corpus` の manifest の Apalache は 0.62.4**（0119 は 0.63.0）。jar と archive は provenance の hash だけに使われる。
- **audit の縮小。** `evals/runs/0120-audit/` は plan の記録の規則（summary だけを commit する）に合わせて縮小し、driver は `evals/experiments/call-depth/audit-0120/` に移した。消した数・バイト数・digest は `reduced.json`、生の出力は untracked の `target/0120-audit-raw/` にある。

## 評価で見つけた点

1. **F5c の対照が効かなかった**（上の判断）。評価の時点では frozen の test を変えず、追加する対照の案を audit に置いた。その後、correction-0003 で対照を追加し、最終レビューで境界の導出と値の誤りを指摘され、correction-0004 で直した（導出は [correction-0004](../runs/0120-audit/corrections/correction-0004-snapshot-control-boundary.md)）。plan の「期待値が変わる既存のテスト」の範囲外の変更である。
2. **stack の予測が外れた**（「0119 の最大を超えない」）。採否の条件（1,024 / 6,144 KiB）は満たしている。
3. **Go の期待値**: plan は hop の N = 125 を `complete 5 6 1282` と書くが、Go の driver が使う wrapper なしの入力では work は 10N + 27 = 1,277（wrapper つきの入力が 1,282）。期待値は wrapper なしの式（10N + 27、5 の倍数の手前の N は 2N + 7）で照合した。
4. **観測用の複製の patch が 2 つ**（plan は 1 つ）。`descend` の本文が before と after で違うため。
5. **Apalache 0.63.0 の module が評価者の環境にない**ので、`chain-N50` の TLC は 0119 の記録を引用した。
6. **TLC の起動表示**は `Version 2.19 ... rev: 5a47802` で、plan の「1.7.4」と revision が一致する。
7. **「複製で確認する」と印を付けた値の一覧は、`target/0120-stage-t/` の中に見つからなかった。** 代わりに、frozen の期待値のうち複製から導ける全部（4 経路の 1,194 セル）と、宣言した深さ 100 を複製の記録と照合し、差は 0 だった。
8. **評価の手順**: 異なる source の tree で cargo の target directory を共有すると、成果物が新しいと誤判定される場合があった（最初の並列 probe の build）。tree ごとの target directory に直して取り直し、最初の記録は使っていない。
9. **`published256` の byte の比較は、key の順で全セルが外れた**（保留していた段）。driver が応答の text の digest を持つようになって初めて分かった。最終レビューの指摘で probe を product の直列化に直し、全 4 build を取り直して 138 / 138 が byte 単位で一致した。以前の分析（正規化した応答を比べた）は、この点を見逃していた。
10. **TLC の「判定しない」を数えるようにした。** 以前は label の件数から数えていたが、新しい分析は slice ごとに判定しないセルを全部列挙する（115 行）。最終レビューの指摘で、判定を `tlc-judge-0120.ts` に切り出し、予期しない error（例: `Missing lexical call frame`）と、TLC が違反か 0 除算に達する入力での after の 256 の拒否・`bounded` を不一致に数えるようにした。欠陥のある入力を流す `--self-test` を足した。さらに、TLC が complete で `oracle-after` の hit が 0 のセルでは、after の `bounded / work`・256 の拒否・before にない compile の拒否も不一致に数えるようにし、`--self-test` を 20 件にした（`hop-invariant-124` の after の結果を `bounded / work`・256 の拒否・compile の拒否に差し替えた複製の dump では、3 通りとも不一致 1 になった）。保存済みの結果を流し直すと、不一致 0・判定しない 115（slice ごとに 32・37・18・28）で変わらない。
11. **例 C を TLC と比べた。** 最終レビューが指摘した、plan の「TLC の違反の trace とも比べる」の記録を取った。
