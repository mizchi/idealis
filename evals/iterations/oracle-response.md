# roracle の応答生成とデコード

TS デコーダは JSON.parse が作った report のフィールド、観測の型、件数を検査し、そのオブジェクトを返す。napi-rs の object 入口は Rust の report を JSON 文字列に直接出力する。入力側の JS 検査と Node-API から Value への変換は引き続き実行する。

## 全リクエストの時間

[事前計画](../plans/oracle-response.md)に沿って、Apple M5・Node v24.22.2 で各段階を順に測った。下表は 30 samples の中央値で、単位は µs。照合と全応答のデコードを含む。初回起動と SUT の実行時間は表に含めていない。

| 入力・経路                   | 変更前 | TS デコーダのみ | Rust 直接出力を追加 |
| ---------------------------- | -----: | --------------: | ------------------: |
| 32 cases、Wasm               |  76.20 |           76.00 |               76.68 |
| 32 cases、native JSON        |  66.33 |           66.61 |               67.65 |
| 32 cases、native object      | 247.82 |          251.48 |              233.16 |
| 入れ子256要素、Wasm          | 198.43 |          198.97 |              197.28 |
| 入れ子256要素、native JSON   | 157.63 |          159.80 |              155.67 |
| 入れ子256要素、native object | 738.29 |          758.27 |              701.58 |

TS の変更で検証後の再構築を除いた。全リクエストの速度に一貫した改善は見られなかった。Rust 直接出力を加えた段階では、一つ前の段階と比べて native object の時間が両入力で約7%短かった。順次測定であり、個々の差には段階間の実行環境の変動も含まれる。最終段階でも native object は Wasm の約3.0倍、3.6倍の時間を要した。

## 検証と利用箇所

3段階で6入力の fixture と期待 report の一致を確認した。各段階で Wasm と両 native 経路の18応答を再生し、保存した540 warm samples と30 cold samples の集計を照合した。Rust のテストは Value と直接出力の全応答およびエラーを照合する。TS は壊れた入れ子の観測を拒否し、検証した report の参照を返す。[測定値・ソース・バイナリの保存記録](../runs/oracle-response/evidence.json)

コンパイラの評価に、同じ期待値を Wasm と native の結果に各1回使う箇所がある。ここで期待値を登録すると登録・照合2回・解放が必要になる。登録費用を回収できる頻度は未計測のため、ハンドル API の追加は見送った。[呼び出し箇所](../rtla-compiler/evaluate.ts)
