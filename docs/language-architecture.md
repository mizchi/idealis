# Idealis 言語の設計

`.ideal` は、ドメインで考える望ましい振る舞いを記述するソースファイル。名前にはプラトンのイデアのニュアンスがある。用語、状態、操作、守るべき性質をつなぎ、形式検査と実装照合で同じドメインの名前を使えるようにする。

## モデルと検査の境界

| 責務       | 所有するもの                                               | 現在の置き場                                                   |
| ---------- | ---------------------------------------------------------- | -------------------------------------------------------------- |
| 構文       | `.ideal` の表記、構文木、ソース位置                        | `idealis-syntax`                                               |
| モデル     | 名前解決、型検査、検査済みの宣言・式・性質                 | `idealis-syntax` の `Model` と `CheckedModel`                  |
| 意味論     | 初期状態、操作の有効性、同時更新、スコープ逸脱             | `idealis_semantics::reference`                                 |
| 仕様の対応 | ユビキタス言語、自然言語の規則、モデルの性質と実装への参照 | `idealis-spec`。現在の文書入力は Pkl                           |
| 検査と照合 | 検査器の選択、予算、判定、反例、実装観測と ITF             | `idealis-check`、各検査器、`idealis-core` のポータブル実行 API |

今回の分離では `idealis-syntax` を `idealis-semantics` が参照する。型生成と Alloy・TLA+ への変換は `idealis-model` に置き、構文と参照評価器の型を同 crate からも利用できるようにする。`idealis-core` はポータブルな実行 API を持つ。今の `FiniteModel` は、状態と遷移を列挙した実行・再生用の形式。型検査済みの宣言モデルから生成できる形として位置づける。規則と用語は安定した ID で参照し、形式的な性質、検査結果、実装上の観測をたどれるようにする。自然言語の規則を `.ideal` に書く構文は設計中。

意味論は操作をしたとき何が起こるかを決める。探索予算、検査器の対応範囲、反例を発見したかは検査結果に記録する。各バックエンドは検査済みモデルを受け取り、結果と証拠は元のモデルで照合できるようにする。[核の意味論](kernel-semantics.md) · [検査器の契約](backend-contract.md)

## 一つのモデルから検査を組み合わせる

`.ideal` には、業務用語と状態・操作・性質を一度ずつ書く。図書館なら `LoanIsRecorded` がすべての到達状態についての性質、`RenCanBorrow` が到達経路の存在を問う性質になる。これらの名前を、自然言語の規則とのリンクや検査結果で共通に使う。[図書館モデル](ideal-tutorial.md)

有限スコープは、たとえば「蔵書1冊、名前付き会員2人」という一回のモデル化の前提になる。SAT に何状態まで渡すか、探索にどれだけ予算を使うかは実行時に指定する。現行の `scope Copy = 1` はモデルに残し、SAT のトレース長には `--sat-steps` を使う。蔵書数を変えれば問いの対象が変わり、トレース長を変えれば同じ問いに対して得られる証拠が変わる。

検証計画を導入するなら、最小の単位は「モデルの参照、性質名、期待する判定、必要な証拠」とする。各実行は検査器・上限・予算を指定し、結果には実際に使ったスコープとカバレッジを残す。次の表は図書館で必要な証拠の例。現時点では個別コマンドで実行でき、計画を記述する新しい構文は保留する。

| 性質             | 期待       | 合格に必要な証拠                                                 |
| ---------------- | ---------- | ---------------------------------------------------------------- |
| `LoanIsRecorded` | 成立する   | 指定スコープ内で全到達状態を検査し、違反がない                   |
| `RenCanBorrow`   | 到達できる | 指定スコープ内の初期状態から、条件を満たす状態への経路が得られる |

成立や到達不能の合格には完全な検査が要る。到達や違反は有界探索で得た経路でも示せる。経路を証拠として保存するときは元のモデルで再生し、経路が出力されない実行の判定とは区別する。初期状態なし、対応外、予算切れはそれぞれの理由を残す。検査器の判定を直接突き合わせるときは、モデルの版、性質、有限スコープ、初期条件や公平性などの仮定をそろえる。その上で、有界で未発見という結果と、より長い経路での発見は両立する。

蔵書1冊の実測では、SAT を初期状態だけの1状態に制限すると `RenCanBorrow` は有界の `unreachable`、2状態にすると `reachable` になった。参照評価器・明示検査・rprob は1操作での到達を報告し、参照の経路は Ren が `Copy0` を借りる1操作だった。`LoanIsRecorded` は SAT の2状態で有界の `holds`、参照評価器では完全な `holds` だった。同じ `--expect holds` の終了コードはそれぞれ3と0だった。

同じソースから生成した TLA+ では、TLC 2.19 が `LoanIsRecorded` の正常版で4状態を検査し、貸出履歴の更新を外した対照では最初の貸出で違反を返した。参照・明示・SAT・rprob もその対照を検出した。`RenCanBorrow` の生成物は条件の否定を不変条件にするため、TLC の違反が到達の証拠になる。この判定の読み替えは TLA+ 変換側が負い、業務側では `reachable` のまま書ける。[生成器の実行例](../crates/idealis-model/examples/emit.rs) · [期待判定の CLI 契約](../crates/idealis-check/README.md#check-an-expected-verdict-in-ci)

## 再利用できる実装

Idealis が接続層を通して外部形式やエンジンを利用する。TLA+ のパーサー、コンパイラー、探索器や Alloy・SMT-LIB の実装は、Idealis 固有の用語や `.ideal` への依存を持たずに単独で使えるようにする。

| 名前                                               | 位置づけ                                                                   |
| -------------------------------------------------- | -------------------------------------------------------------------------- |
| `rtla`・`rtla-compiler`・`rtlc`・`ralloy`・`rusmt` | 他の形式に対応する再利用可能な Rust 実装                                   |
| `idealis-spec`                                     | Idealis の用語、規則、性質、実装の対応                                     |
| `rprob`                                            | ProB に着想を得た Idealis 向け探索器。将来の名前の候補は `idealis-explore` |
| `rquint`                                           | Quint IR から TLA+ への変換器。独立配布時の名前の候補は `quint-to-tla`     |
| `idealis-check`                                    | Idealis の検査・照合 CLI。将来の入口の候補は `idealis check`               |

## 移行

- 変換と型生成の crate は `idealis-model`、検査・照合の crate とコマンドは `idealis-check`。Rust から参照する場合の名前は `idealis_model` と `idealis_check`。
- 新しいソースは `.ideal` を使う。単独ファイルと、`.project.json`・`.component.json` に含まれる断片を読める。旧拡張子の `.model` と `.rmodel.json` も引き続き読める。
- 仕様リンクのクレートは `idealis-spec`。Pkl の入力形式、規則 ID、既存の照合リビジョンのハッシュ方式は引き続き利用できる。
- TLA+ ソースの読み込みとバンドルのコンパイルは `rtla-compiler` が担当する。既存の `idealis_core::compile_tla` と Wasm リクエストは、その API を呼ぶ入口として使える。
- `idealis-check` はソースと JSON IR の両方を `idealis-syntax` が所有する `CheckedModel` に通す。`idealis_model::CheckedModel` は同じ型の再公開。`rprob` と `idealis-spec` のライブラリは新しい両 crate を直接使う。
- crate の分離を先に行い、既存の評価規則を精査する作業は次の段階とする。分離の検証では IR、生成物、判定と反例を照合する。
