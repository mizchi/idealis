S3 の契約は、成功応答のあとに開始した読み取りの強い整合性。キー間の原子性や並行更新の順序はモデルの対象外。[Amazon S3 の整合性モデル](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html#ConsistencyModel)

同時編集の接続は、1個の強い ETag を `If-Match` で送る。条件を満たさない保存には `412 Precondition Failed` を返す。[RFC 9110 §13.1.1](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.1)

ストリームの例は読み取り側の high-water mark を0にし、読み手が要求した順に値を渡す。変換中の `error()` は読み取り側と書き込み側を両方エラーにする。[Node.js Web Streams API](https://nodejs.org/api/webstreams.html#transformstreamdefaultcontrollererrorreason)

## 自分の環境につなぐ

`@mizchi/idealis/patterns` の関数は、モデル、初期状態、標準の操作列をまとめた `scenario` と、渡した環境につなぐ `adapter` を返す。既定のモデルはパッケージに同梱されている。別のモデルを使う場合はパスを引数で渡す。[配布パッケージの使い方](../../docs/model-patterns.md)

| 関数                                     | 利用側から渡すもの                                                                    | 開始時の状態                  |
| ---------------------------------------- | ------------------------------------------------------------------------------------- | ----------------------------- |
| `browserHistoryPattern(history, routes)` | ルーターの移動操作、URL と DOM を読む関数、`Home`、`Catalog`、`Detail` と実画面の対応 | `Home` を表示した新しいページ |
| `nodeIoBatchPattern(batch)`              | I/O 内でバッチを実行し、完了後に実行されたコールバック名を順に返す処理                | コールバック記録が空          |
| `nodeNextTickPattern(batch)`             | `nextTick` と microtask の登録位置を区別して、実行順を返す処理                        | コールバック記録が空          |
| `objectStorePattern(store, testKey)`     | ストアの4操作と、この検査専用のキー                                                   | キーが未存在                  |

Chromium の例ではモデルの `Detail` を製品の `/product` に対応付けている。自分の型や初期状態から異なるシナリオを組む場合は、以下の分割モデルと各アダプターを直接使える。

Node.js の動作を手元で確かめるなら、読めるファイルを [nodeFileIoBatch](node-event-loop/file-batch.ts) に渡す。アプリ内の I/O と照合する場合は、その処理に接続した `IoBatch` を渡す。

```ts
const { scenario, adapter } = nodeIoBatchPattern(nodeFileIoBatch(new URL(import.meta.url)));
const result = await recordReplay(checkerPath, scenario, adapter);
```

`nextTick` の例では、`nodeNextTickPattern(nodeFileNextTickBatch(file))` に読み取れるファイルを渡す。アプリ側のバッチも同じ `IoBatch` インターフェースにつなげる。I/O から登録した `nextTick` は2件の microtask より先に、1件目の microtask から登録した `nextTick` は2件目より後に記録される。記録の再検査には `nextTickProjection` を渡す。[Node.js のキュー仕様](https://nodejs.org/download/release/latest-v24.x/docs/api/process.html#when-to-use-queuemicrotask-vs-processnexttick)

履歴・FIFO・オブジェクトストアの `model.project.json` は、対象の型宣言と操作の断片を順に読み込む。履歴では `routes.ideal` の `Route` を実際の画面名に置き換える。オブジェクトストアでは `values.ideal` の `Body` を有限のテストデータに対応付ける。FIFO では `messages.ideal` の `Message` を変更できる。有限列の値の上限を超える場合は、メッセージ種類かキュー長を絞る。型名と操作名が接続点になる。

[replay](replay.ts) にはモデル、設定、初期状態、操作列と次のアダプターを渡す。一致を確認できる範囲は、ここで選んだ観測項目。

- `apply(command)` は対象環境で操作を実行し、次の観測を取れるまで待つ。
- `observe()` は対象環境から値を読む。たとえば画面テストではURLとDOMの両方を読む。
- `project(state)` はモデルの状態から比較できる項目を取り出す。

毎回 `idealis-check validate` が初期状態と操作列を確認してから次の操作を呼ぶ。最初の食い違いで停止し、手数、操作、期待値、実測値を返す。正常版と故障版に同じ操作列を渡せる。[画面・I/O・オブジェクトストア](../../tests/model-patterns/patterns.test.ts) · [FIFO・検索・worker](../../tests/model-patterns/concurrency.test.ts)

### AWS S3 につなぐ

利用側に AWS SDK v3 の `@aws-sdk/client-s3` を入れ、集合クライアント `S3` とバケット名を [s3ObjectStore](object-store/s3.ts) に渡す。クライアント側でリージョンと認証を設定する。検査にはバージョニング未有効の検査用バケットと、他の処理と共有しない未使用のキーを使う。

以下はテスト専用キーに `V1` を書き、`V2` に上書きしてから削除する。操作後の GET と LIST を、成功応答のあとの読み取りに関する [S3 の整合性モデル](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html#ConsistencyModel) と照合する。開始時に既存キーが見つかれば書き込み前に停止する。LIST は全ページを読み、GET の `NoSuchKey` を未存在に写す。権限不足や通信エラーはそのまま呼び出し元に返る。

```ts
import { S3 } from "@aws-sdk/client-s3";
import { objectStorePattern, recordReplay, s3ObjectStore } from "@mizchi/idealis/patterns";

const store = s3ObjectStore(new S3({ region }), bucket);
const { scenario, adapter } = objectStorePattern(store, testKey);
const result = await recordReplay("crates/idealis-check/target/debug/idealis-check", scenario, adapter);

if (result.verdict === "mismatch") {
  console.error(result.difference); // step, command, expected, observed
}
```

SDK アダプターの回帰試験はローカルで動く。AWS 上の実バケットでの検証は未実施。[アダプターの回帰試験](../../tests/model-patterns/s3.test.ts)

最初の不一致や通信エラーで実行が止まるため、書き込み済みの検査キーが残る場合がある。

到達性の問いから操作を始める場合は、`reachableScenario(checkerPath, model, question)` で構成・初期状態・操作列を取得する。得られた操作列に確認したい操作を足して `replay` に渡せる。購読の例は、通知待ちのまま再登録した状態と、通知開始後に購読した状態への経路を生成する。

## 保存した観測から差を再現する

注文・決済の例では、保存した中間状態を ITF の有限トレースとして書き出し、ファイルから同じ差分を再現する。[ITF の再照合](checkout/README.md#itf-ファイルから再照合する)

`recordReplay` は `matched` または `mismatch` と、保存用の `recording` を返す。記録にはシナリオと、操作前から差が出た手までの観測値が入る。モデルが操作を受け付けなかった場合や、環境に接続できなかった場合は例外になる。

JSON 互換の値を観測するアダプターなら、`JSON.stringify(result.recording)` で保存できる。モデルとアダプターのリビジョンも一緒に記録する。同じリビジョンで `replayRecording` に観測の記録と比較用の関数を渡すと、環境に接続せずに判定と最初の差分を取得できる。操作前または途中の観測が欠けていればエラーになる。

```ts
const result = await replayRecording(checkerPath, saved, browserScreenProjection(routes));
```

Node.js なら `ioBatchProjection`、S3 なら `objectStoreProjection` を渡す。3つの関数は [library.ts](library.ts) から読み込める。Chromium のテストではページを閉じたあとに、戻る操作で起きた URL と画面の食い違いを再現する。

## 実行

Chromium を利用できるリポジトリのルートで実行する。

```sh
just model-patterns-test
```

故障対照は、戻ったURLに画面が追随しない場合、コールバックの順序が変わる場合、上書き後の古い本文と LIST からの欠落を検出する。

並行性の対照は、FIFO を末尾から取り出す故障、古い Promise が画面を上書きする故障、二つの worker が読み取った値を元に書き戻して増分を失う故障を検出する。worker の観測には共有メモリ上の値と、読み込み済みの値を使う。二項の `lone` の初期状態は、各 worker に `null` を入れる。

ロックの例は、取得が失敗すると次に進めないプロトコルを、操作ごとに worker へ指示して観測する。実時間のタイムアウトは使わず、逆順では両方の取得が相手に阻まれたことを確認する。同順では両方が解放まで完了する。

再送の例では、DB を閉じる前に確定記録と台帳を同じトランザクションで書く。再接続後も元の ID への書き込みは一度で、別の ID は独立に確定する。応答の消失はテストから指示する。

強制終了の例は、準備書き込みまたはコミットを子プロセスが通知した直後に `SIGKILL` を送る。準備書き込み後は再起動時に両方の記録が空で、再処理できる。コミット後は両方が残り、再処理なしで受領記録を返す。台帳だけを先にコミットする故障では、準備書き込み後に停止すると再起動時に台帳だけが残る。

ロックの公平性は、無制限に続く待ちをモデル検査器で調べる。`GroupStrong` と `InstanceWeak` は取り合いで破れ、`InstanceStrong` と `FifoWeak` はそれぞれのモデルで成立する。実装の照合では有限の操作列を渡し、FIFO の先頭以外が実際の取得を試みても拒否されることを確かめる。

アウトボックスの接続テストは二つの停止地点を `idealis-check witness` で生成し、再起動と再送を足す。送信済み記録を失うと同じ ID の HTTP リクエストは2回届く。正常版では受信側の効果は1回だけ残る。停止は送信側の接続を閉じ、未記録の応答を捨てることで再現する。

アップロードでは、新しい結果が表に出た時点で古い要求が通信中、保存中、または応答待ちにある操作列を `idealis-check witness` で生成する。Chromium が送った HTTP 要求は試験から指定した順に通す。サーバーはブラウザが送った選択順の番号で最新の受理を決める。到着順だけを使う故障や、最新の受理を無視して公開する故障は7手目、古い応答で画面を巻き戻す故障は8手目で検出した。[Chromium とローカル HTTP の接続試験](../../tests/model-patterns/upload.test.ts)

決済の補償では、在庫引当サービスが失敗を返すと、決済サービスは返金を SQLite に確定する。確定直後に HTTP 接続を切り、同じキーで再送しても返金が増えないことを確かめる。弱公平性の下では、応答を失い続けて取り消しが確定しない循環がある。[返金再送の接続試験](../../tests/model-patterns/compensation.test.ts)

時相の反例は `repeatedTemporalScenario(checkerPath, model, question, repetitions)` で有限回の操作列にできる。停止ステップは実装への呼び出しを発生させない。循環の入口までを再生する場合は `repetitions = 0` を使う。停止だけで構成される循環では、この入口までを操作列にできる。返金では、弱公平性の反例の循環を3周再生し、返金台帳には1件が残り、注文はまだ返金待ちであることを確認する。

共有レジスタでは、`idealis-check witness` で A→B→A の経路を作り、二つの Node.js worker に渡す。値と世代を一つの整数に詰め、`Atomics.compareExchange` の返り値から成功を判定した。検査範囲は他方の更新が最大2回。4種類の世代を使う版は古い CAS を拒否し、世代を持たない版と1ビットで一周する版は4手目で古い CAS が成功した。[実行テスト](../../tests/model-patterns/aba.test.ts) · [ECMAScript の Atomics.compareExchange](https://tc39.es/ecma262/multipage/structured-data.html#sec-atomics.compareexchange)

再利用バリアでは、速いワーカーが第2ラウンドに到着し、遅いワーカーがまだ第1ラウンドを抜けていない4手の経路を探索する。二つの Node.js ワーカーでこの経路を再生する。待機の確認で現在の世代を照合する版は、第2ラウンドでも両者が揃うまで進まない。前のラウンドの解放を使い回す故障は5手目で速い側だけが完了した。検査ではタイムアウト0の `Atomics.wait` で待機の判定を観測する。[接続試験](../../tests/model-patterns/worker-barrier.test.ts)

読み取りロックの昇格では、読み取りを持ったまま待つ対照から `deadlock --ignore-stutter` で4手を得た。二つのワーカーに再生すると、どちらが昇格を試しても状態が変わらない。読み取りを手放す方式では先に通った側が書き込み、遅い側は読んだ版が古くなったため書き込まない。版の比較を省く対照は8手目で先行の書き込みを上書きした。[接続試験](../../tests/model-patterns/worker-upgrade.test.ts)

当直交代では、rprob が返した4手の反例を SQLite WAL の二つの接続で試す。読み取りを保持した版は遅い書き込みを `SQLITE_BUSY_SNAPSHOT` で拒否する。再試行で読み直すと最後の一人には退勤を許可しない。読み取りを先に終了してから古い判断で書き込む対照は、4手目で当直が空になった。[SQLite の分離](https://sqlite.org/isolation.html) · [接続試験](../../tests/model-patterns/sqlite-write-skew.test.ts)

名簿を元に戻す例では、読み取りを保持する方式と新しいトランザクション内で版を比較する方式を同じモデルに照合する。両方とも後着の書き込みを拒否し、名簿の中身だけを比較する故障版は4手目で確定する。[復元を含むモデル](sqlite-transactions/snapshot-aba.ideal) · [接続試験](../../tests/model-patterns/sqlite-write-skew.test.ts)

複数通知の例では、同じ購読名への通知を2件まで保留できる。古い登録を解除し再登録したあとも、古い通知は新しい登録に届かない。発行を再登録の前後で分けた場合は、新しい通知だけが新しい登録に届く。現在の登録へ通知を付け替える故障は接続試験の6手目、同じ登録を宛先に持つ別の通知まで消す故障は4手目で検出した。[実行テスト](../../tests/model-patterns/queued-notifications.test.ts)

通知 ID の再利用では、`idealis-check witness` が古い確認を再送できる状態と、同じ世代を持つ二つの通知が待つ状態への経路を生成する。MessageChannel で受け取った ID と世代を、SQLite の保留レコードの両方の列に照合する。以前の世代への確認を再送しても現在の保留は維持され、現在の世代への確認で初めて取り除かれる。世代だけを使う故障は別 ID の通知まで確認済みにする。[実行テスト](../../tests/model-patterns/notification-ack.test.ts)

待機と通知では、早い通知が誰も起こさずに戻ったあと、待機側が条件の値を比較して先へ進めることを確かめる。条件と別の共有位置で待機する故障では、早い通知のあとでも待機に入る。条件が偽のまま通知された場合は、起床後に条件を読み直す。故障の操作列は、時相反例の停止地点までを使う。[実行テスト](../../tests/model-patterns/wait-notify.test.ts) · [ECMAScript の Atomics.waitAsync](https://tc39.es/ecma262/multipage/structured-data.html#sec-atomics.waitasync)

共通の待機列では、登録順が左・右で、右の条件だけが成立する操作列を生成する。1件だけ通知すると左が起き、右は次の通知で起きる。2件に通知した場合は両方が起き、条件を満たした右だけが処理を完了する。[実行テスト](../../tests/model-patterns/selective-notify.test.ts) · [ECMAScript の待機列からの取り出し](https://tc39.es/ecma262/multipage/structured-data.html#sec-removewaiters)

資源の受け渡しでは、試験から AbortController でタイムアウトを発生させる。受領前のタイムアウトでは予約を返し、遅れて受領処理が走っても取得結果は取り消しのまま。受領後にタイムアウトが届いた場合は、明示的な返却まで所有が続く。[実行テスト](../../tests/model-patterns/lease.test.ts)

再貸出では、新しい貸出と書き込み先の最小世代を同じ SQLite トランザクションで更新する。古い世代の返却・書き込みに続けて現在の世代で書き込み、貸出と本文を確認する。古い返却で新しい貸出を消す故障は4手目、最小世代の更新を新しい世代の最初の書き込みまで遅らせる故障は5手目で検出した。[実行テスト](../../tests/model-patterns/lease-fence.test.ts)

別ストアの例では、書き込み先の世代を登録する前、登録直後、確認直後で貸出管理の接続を閉じる。再開後は同じ世代を登録し直して確認し、貸出を有効にする。準備済みの貸出を再開時にそのまま公開すると、書き込み先の下限が古いままで、古い書き込みが通る。[実行テスト](../../tests/model-patterns/split-lease.test.ts)

保存先の切り替えでは、切り替え後に旧保存先へ現在の世代で書く操作と、新保存先へ古い世代で書く操作を送る。旧保存先への書き込みを通す故障は4手目、本文だけを複製して古い世代を通す故障は5手目に観測した。[実行テスト](../../tests/model-patterns/store-cutover.test.ts)

差分ログを圧縮したあと、削除済みの最終位置と複製の位置が等しい場合は次の差分を適用できる。複製の位置が古ければスナップショットを取り直す。採取後に圧縮が進んで再び欠落した場合も、次の取得で欠落を通知する。SQLite の照合では、通知を欠く故障を3手目、採取後の最新位置を採取済みデータに付ける故障を6手目で検出した。[圧縮されたログの接続試験](../../tests/model-patterns/feed-compaction.test.ts)

再同期の例では、古い要求のほうが先の位置を採取する経路と、現在の要求の採取位置が差分適用に追い越される経路をモデルから生成する。どちらも実際の HTTP 応答を指定した順で返し、受信側の公開位置と集計値を比較する。要求の世代と採取位置の比較をそれぞれ外すと、8手目で異なる値が公開された。[再同期の接続試験](../../tests/model-patterns/resync-order.test.ts)

原本の切り替えでは、切り替え先の初回位置1を受け入れ、差分で位置2に進む。現在の要求に対して旧原本が位置2を返しても、切り替え先の本文を保つ。旧原本との連番比較と、応答の原本を確認しない故障を個別に再現する。[接続試験](../../tests/model-patterns/resync-source.test.ts)

同じ原本名へ戻る試験では、切り替え前に A が採取した HTTP 応答を、同じ URL に戻ってから送る。古い保存値を読む故障は4手目、遅れた応答で古い値を保存する故障は5手目で検出する。現在世代の A から採取し直すと、旧応答と同じ位置1で新しい本文を読める。[接続試験](../../tests/model-patterns/resync-reused-source.test.ts)

オフライン編集の試験では、別の項目を編集した場合と、同じ値への編集が重なった場合はマージする。別々の値へ変更した場合は全文書を保って競合を返す。全文置換、競合の無視、競合時の部分反映を、生成した操作列の最後の提出で検出する。[SQLite との照合](../../tests/model-patterns/offline-merge.test.ts)

オフライン編集の再送では、編集のコミット後に HTTP 接続を切断し、SQLite を開き直す。別の編集で現行版が進んでも、同じ要求は最初の確定結果とその版を返す。同じ ID で本文を変更した場合は拒否する。[応答消失の接続試験](../../tests/model-patterns/offline-retry.test.ts)

再送記録の削除では、受付の下限を保存してから期限切れ世代の記録を消す。SQLite を開き直したあとも旧世代は拒否され、境界と等しい世代の再送には元の版が返る。同じローカル ID を新しい世代で発行した場合は受け入れる。[接続試験](../../tests/model-patterns/retry-retention.test.ts)

同期バッチの試験では、最初の項目を確定してから HTTP 接続を切り、SQLite を開き直す。同じバッチを送り直すと、部分応答には確定した項目だけが入り、残りの項目が確定すると完了応答になる。[HTTP・SQLite の照合](../../tests/model-patterns/batch-retry.test.ts)

HTTP のドレインでは、受理済みの応答を保留したまま受付を閉じる。後続の要求には実際に503を返し、先の応答を届けてから停止する。完了処理の公平性を外して得た反例は、停止を試しても保留が残る循環をローカル HTTP で3周再生する。[ドレインの接続試験](../../tests/model-patterns/http-drain.test.ts)

ドレイン期限の試験では同じ論理期限に完了と打ち切りを両順序で実行する。先に完了した場合は本文を届け、先に打ち切った場合は接続を切る。どちらも後続のコールバックは結果と資源の解放回数を変えない。[期限の接続試験](../../tests/model-patterns/drain-deadline.test.ts)

ストリームの試験は、送信後にまだ読んでいない時点と、読んだあとにまだ処理を確定していない時点の両方で接続を切る。SQLite を開き直し、最後に確定した位置から未確定分を取り直す。境界と同じイベントが再送されても処理件数を増やさない。[再接続の試験](../../tests/model-patterns/stream-resume.test.ts)

EventSource の自動再接続では、Chromium が最後に受信した ID を送る間に、別の HTTP 操作で行うアプリの確定が遅れる場合を再現する。ヘッダーが2で確定位置が1なら、正常版はイベント2を再送し、故障版はイベント3を送る。イベント2を確定したあとに同じ ID と本文を再送すると、正常版は適用件数を2件に保ち、二重適用する故障版は3件になる。[Chromium の接続試験](../../tests/model-patterns/event-source.test.ts) · [HTML Standard の Last-Event-ID](https://html.spec.whatwg.org/multipage/server-sent-events.html#the-last-event-id-header)

共有ログを読む二つの購読者は、別々の進捗を持った状態で接続を開き直す。両方の接続が開いてから、位置1の購読者にはイベント2、位置2の購読者にはイベント3を送る。書き込みと再開位置を誤って共有する故障を個別に検出する。[二購読の接続試験](../../tests/model-patterns/multi-stream.test.ts)

購読の進捗に差がある間は遅い購読の確定位置を越えて削除しない。失効後に境界が進んだら、古い位置での再接続には409を返す。位置が境界と等しい場合はそのまま再開できる。スナップショットを取り直すと新しい位置から購読を保護する。[保持と再取得の試験](../../tests/model-patterns/stream-retention.test.ts)

フィルター付き購読の例では、位置1の対象外イベントを読み飛ばして削除する。位置2の対象イベントが未確定なら、位置3を走査済みでも位置1までしか通知できない。走査位置をそのまま確定する故障を再接続まで追うと、位置2が適用されないまま位置4を受け取る。[進捗通知の接続試験](../../tests/model-patterns/filtered-stream.test.ts)

共有取得の試験では、最初の待ち手がキャンセルしても、残った待ち手に本文が届く。二人ともキャンセルした場合は基礎の HTTP リクエストを中断する。どちらもサーバーへの取得要求は一件。[共有取得の接続試験](../../tests/model-patterns/shared-fetch.test.ts)

取得キーの再利用では、古い HTTP リクエストを中断したあとも Promise の後処理を保留しておく。同じキーの新しい取得が登録されたあとに古い後処理を解放し、次の呼び出しが新しい取得に合流することを確認する。キーだけで削除する故障では3件目の取得が発生する。[登録と後処理の接続試験](../../tests/model-patterns/shared-fetch-generation.test.ts)

子タスクの終了を待つ例では、一方を失敗させて他方へキャンセルを送り、それぞれの Promise の `finally` を別々に解放する。親は両方の終了後に最初の失敗のエラーを返す。成功経路でもすべての終了を待つ。[タスクグループの試験](../../tests/model-patterns/task-group.test.ts)

親のキャンセルと子の失敗はどちらの順でも発生させる。キャンセルを通知された子が停止する前に別の失敗を報告しても、そのエラーは記録し、親は最初の理由を返す。最後の後片付けまで親が待つ点も照合する。[終了理由の接続試験](../../tests/model-patterns/task-group-cause.test.ts)

作業と後片付けの両方が失敗する例では、最後の子が終了したあとに元の作業エラーと後片付けの失敗を返す。作業に失敗がなくても、後片付けに失敗したグループはエラーを返す。[エラー集約の試験](../../tests/model-patterns/task-group-cleanup.test.ts)

終了と追加が競合する例では、受付を閉じる前に追加された子を待ち、閉じた後の追加は起動前に拒否する。閉じた後の追加を許すと、親が戻ったあとも子が残る。[受付境界の試験](../../tests/model-patterns/task-group-admission.test.ts)

ワーカープールの停止では、待機中の仕事を取り消し、実行中の仕事が終わるまで停止を待つ。予約のコールバックが停止後に届いても仕事を起動しない。稼働中に同じコールバックを実行した場合は、ワーカーで仕事を開始できる。[停止の試験](../../tests/model-patterns/worker-pool-stop.test.ts)

ワーカー異常終了の例では、応答前にスレッドがエラーを投げたことと非ゼロの終了コードを確認する。枠を解放した後に代替ワーカーで次の仕事を開始・完了する。枠を残す故障では代替が起動しても待機したままになる。[異常終了の試験](../../tests/model-patterns/worker-pool-crash.test.ts)
