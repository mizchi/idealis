# 自然言語・DDD・形式仕様・証明をどうつなぐか

近い先行研究はある。**GE の ASSERT は、業務で使う概念を型付き語彙にし、制御英語の要件から定理証明・反例探索・テスト生成までつないだ**。**UDML は、DDD を明示し、ドメインの構造・操作・アクセス方針を一つの実行意味論に載せて Event-B の証明義務を生成した**。自由記述と時相検査を含む実践例には ProR と Event-B の統合がある。今回確認した一次資料では、任意の自由文、戦略的 DDD の Bounded Context、実行可能な形式仕様、機械証明を一つの表面文法で扱い、すべての対応を検証した事例は見つからなかった。Idealis では、仕様の入口を自由文・制御自然言語・既存 DSL に開きつつ、**機械的に検査する意味を型付きモデルと名前付きの性質に集約する**設計が、この文献群に最もよく支えられる。 [ASSERT、IEEE RE 2018](https://www.khoury.northeastern.edu/home/pete/pub/re-2018.pdf) · [UDML、2026](https://doi.org/10.25073/2588-1086/vnucsce.6743) · [Hoang ら、2018](https://doi.org/10.1016/j.scico.2017.11.002)

## 発送の規則を二つの文法で書く

既存の Idealis では、`acknowledge` が追跡方法を変更しない性質を `transition ShippedStays` に書き、自然文の `SHIPMENT-TRACKING` から参照している。Rust・TypeScript・Go で同じ Courier／Post の ITF を再生し、追跡方法を上書きする故障を特定の操作で検出できた。自然文の意味比較は入力を準備した段階で、ライブ判定は未計測だった。この題材なら、モデル・トレースを固定して文法だけを比較できる。 [既存モデル](../fixtures/rcheck/structured/shipped-transition.model) · [再生と仕様比較の評価](../evals/iterations/0118-shipment-drift-and-replay.md)

**案 A は、自由文を既存の性質に結ぶ。** 自由文から作業を始めるときは要件 ID を先に確保し、形式化した時点でリンクを埋める。用語はフルネームかコンテキスト内の名前で参照する。文章・性質・名前解決に使った語彙の版をレビュー記録に残し、どれかが変わったら再確認する。ProR に先行例がある方式で、業務専門家が表現を選べる。既存の idealis-spec に近く、実験で追加するのは版の照合と型付きの証明リンクで済む。以下はいずれも未実装の構文案。 [ProR のリンク管理](https://wiki.event-b.org/images/Pror-integration.pdf)

```text
requirement SHIPMENT-TRACKING in Shipment {
  prose ja "発送済みの注文は、実行可能な各操作の直後も発送済みで、追跡方法は変わらない。"
  terms Shipment.status, Shipment.Carrier
  property Shipment.ShippedStays
  proof lean "ShipmentProof.lean" theorem ShipmentProof.shipped_stays
}
```

**案 B は、制御日本語を型付きの二状態式に落とす。** 自然文で指定できる形を「前件」「どのステップを量化するか」「維持する状態と値」から始める。発送の例の「実行可能な操作の直後」はすべての有効なモデル遷移の直後を指す。「追跡方法」は発送済み状態のペイロードに束縛し、後状態のタグを確かめてから比較する。辞書・構文規則・生成式を表示し、コンテキストをまたぐ曖昧な名前や、対応する構文がない文章はエラーにする。型付き詳細を英語や日本語に出力する方向も比較できる。FRETish のパターンと、GF の抽象構文からの自然文生成を組み合わせる設計案である。 [FRET](https://ntrs.nasa.gov/citations/20200001989) · [Grammatical Framework](https://www.cambridge.org/core/journals/journal-of-functional-programming/article/grammatical-framework/09C4B3F43447ADDB0F632C64F195BC9C)

```text
requirement SHIPMENT-TRACKING in Shipment {
  rule ja {
    操作の直前に ［発送状態］ が ［発送済み］ なら、
    実行可能な各操作の直後も ［発送状態］ は ［発送済み］ で、
    ［追跡方法］ は操作の直前と同じ。
  }
  transition ShippedStays generated
  proof lean "ShipmentProof.lean" theorem ShipmentProof.shipped_stays
}
```

案 A の機械化対象は、自然文と形式式の**対応を記録し、変更時に再確認の対象とすること**。案 B では、制御文に意味を与える辞書と規則を固定し、その文から生成した式を機械的に比較できる。どちらでも、モデルから自然文を読み返す表示と、前件が成立する正常トレース・違反トレースを添えると、「どの操作」「いつまで」「何が維持されるか」をレビューで確かめられる。 [透析装置のアニメーション](https://www.southampton.ac.uk/~tsh2n14/publications/journals/hdmachine-scp2017.pdf) · [FRET の要件シミュレーション](https://ntrs.nasa.gov/citations/20200001989)

## 証明ファイルは生成された命題の型で照合する

現行の `idealis-check lean-oracle` は、有限探索で列挙した構成・状態の各スナップショットを外部 Lean ファイルの `main` に渡し、真偽値を受け取る。外部証明を加えるなら、型付きモデルから `Init`、`Step`、到達可能性と性質の `Prop` を生成し、**その `Prop` を期待型として外部定理を Lean カーネルに検査させる**。`before/after` の性質なら、到達状態 `s` と有効な `Step s t` に対する二状態の条件を生成する。証明に使った定理が依存する公理と仮定を記録する。モデルを変更したら再生成・再 elaboration し、型検査を通過した証明を新しい版に対応づける。 [現行 Lean oracle の仕様](../crates/idealis-check/README.md#lean-snapshot-oracle) · [Veil のモデルと証明義務](https://link.springer.com/chapter/10.1007/978-3-031-98682-6_2)

```lean
-- rmodel が生成する照合用ファイルのイメージ
import Shipment.Generated
import ShipmentProof
example : Shipment.Generated.ShippedStays :=
  ShipmentProof.shipped_stays
```

有限探索は具体化したモデルの状態・遷移を調べ、Lean の証明は生成された意味論と仮定の下で命題を検査する。rmodel と Lean の変換が意味を保存するかは別の命題であり、初期段階では同じ小モデルについて初期状態・有効操作・次状態・性質の一致を差分検査する。ITF 再生は実装の観測を指定の操作列で照合する。実装全体の保証に進むなら、実コードの操作をモデル上の遷移へ対応させる観測射影や精密化の条件が要る。 [FRETish の翻訳証明](https://arxiv.org/abs/2201.03641) · [Igloo の実装への精密化](https://arxiv.org/abs/2010.04749)

## 発送と三ノード選挙で、文法が生む違いを測る

| 実験                 | 比較する対照                                                                                                                                                                                   | 結果の判定                                                                                                                                                                                                           |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **発送の文と式**     | 現行文、同義の言い換え、確認時の変更を許す文、存在しない性質名、別コンテキストの同名語。                                                                                                       | 案 A はリンク切れ・名前の誤参照を拒否し、文章を変更したら再レビューに戻す。案 B の対応範囲では言い換えが同じ式に正規化され、変更を許す文は異なる式になる。未対応の文は構文・型エラーとして扱う。                     |
| **発送の実行と証明** | `ship(Courier) → acknowledge`、正常な Post、モデルだけで追跡方法を上書きする故障、実装だけで上書きする故障、同名で別の型を持つ Lean 定理。                                                     | モデルの故障は `ShippedStays` の反例になる。実装の故障は正常モデルの証明を変えずに三言語の ITF 照合で差が出る。同名の別定理は型照合で落ちる。発送済みに到達する正例を伴わせ、前件が成立しないままの通過を拾う。      |
| **Raft の安全性**    | 三ノードの選挙サブモデルで「同一 term に二人の leader がいない」。同一 term に投票先を変更できる対照を用意する。                                                                               | 固定した探索範囲で正常モデルの判定と故障トレースを比較する。帰納不変条件や操作別保存を Lean で検証する場合は、その命題・前提・生成規則を記録する。有界探索の結果にはノード数と term の範囲を付ける。                 |
| **Raft の活性**      | 同じ選挙サブモデルで「安定後に leader が選ばれる」。過半数が通信可能になり、一つの候補が競合するタイムアウトで繰り返し中断されない環境を明示する。通信の配信や選挙処理の公平性を一つずつ外す。 | 前提が成立する実行を用意したうえで、活性が破れる待機・再選挙ループの有無を比較する。進行の仮定には、生存するノード数と通信・処理についての条件を明記する。安全性と活性の別々の判定・前提を読者が説明できるかを測る。 |

Raft の対照は、ノードの二重投票を検査する選挙モデルと、環境条件つきの進行を別に問う実験案である。論文の Raft 実装の保証を再現するには、複製ログや適用結果など選挙より広い状態と対応関係が必要になる。比較前に、対象範囲、空・未確定の扱い、正常・故障の期待判定、読み手に尋ねる前件・量化・公平性の正答を固定すると、読解の改善と検査性能を測れる。 [Raft 原論文 §§5.2, 5.6](https://raft.github.io/raft.pdf) · [Raft の機械検証](https://homes.cs.washington.edu/~mernst/pubs/raft-proof-cpp2016-abstract.html)

私なら案 A を基準にする。現行の Pkl 要件と Idealis で得た正常例・反例をそのままに、要件と定理の版・型が変わったときの挙動を先に調べられる。案 B の採用基準は、同じモデルと証明を保ちながら、**どの操作と状態を量化するか、活性にどんな前提があるかを、読み手がより正確に判断できること**。今回行ったのは一次資料と既存評価の調査で、二つの構文や Lean 生成器の実装・評価は今後の実験に残る。
