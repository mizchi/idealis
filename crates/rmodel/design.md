# rmodel の設計と評価

rmodel で業務の語彙、状態、操作、守るべき性質を一つのモデルに書き、その性質を実行して検査できるようにする。文法変更では、業務ルールを追いやすくすることをゴールにし、既存モデルの意味を保つことを条件にする。[核の意味論](../../docs/kernel-semantics.md) · [文法の意思決定ログ](grammar-decisions.md)

## 設計変更のドメイン

| 用語         | 意味                                                                         |
| ------------ | ---------------------------------------------------------------------------- |
| ゴール       | 変更によって改善したい、利用者の行動や成果。変更ごとに主ゴールを一つ選ぶ。   |
| 設計変更     | 対照となる現行の設計と、評価する版の組。モデルではレビュー対象を一件に絞る。 |
| 意味の証拠   | 一致、差異、空、探索未完了、比較相手なし、未確認のいずれか。                 |
| ゴールの証拠 | 事前に決めた課題と基準での改善、改善なし、悪化、未測定のいずれか。           |
| 採用判断     | 評価中か採用か。評価中の実装も検査や書き比べに使える。                       |

## 最初に検査する性質

この判断規則は文法の試作に適用する提案。評価中の版は、意味の一致とゴールの改善がそろったときだけ採用できる。評価対象の版を変えたら、両方の証拠を未確認に戻す。空の検査、予算切れ、比較相手の欠落からは意味の一致を記録できない。意味の証拠は既存の参照評価器とライブラリのテスト、ゴールの証拠は事前に決めた比較に基づく。

設計判断の状態遷移を rmodel で記述する。有限モデルは一件の変更、二つの証拠、採用状態を扱う。検査対象は判断規則。モデルには二種類の証拠の判定を入力する。証拠の出所や測定の妥当性は評価記録に残す。[設計判断のモデル](../../spec/models/rmodel-calibration.model)

文法の意味を評価するときは、`Model` を範囲・設定・初期状態・遷移・検査のまとまりとして読む。設定は遷移中に変化せず、状態は各時点の値を持つ。遷移が可能かと次の状態は遷移前の状態で決まり、検査結果には探索範囲が伴う。この意味の契約は [核の意味論](../../docs/kernel-semantics.md)に置き、書き方ごとの契約は具体例を参照評価器で実行して確かめる。

## 変更ごとの評価の進め方

1. [文法の意思決定ログ](grammar-decisions.md)に、利用者ができるようになること、現行の対照、改善と判定する基準を書く。[仕様の正本](../../spec/rmodel-design.pkl)の `Rule.text` に、守りたい性質を先に自然言語で書く。
2. 規則から対応する `.model` の検査と期待する判定を参照する。遷移前後の値やパーサーを照合する規則には、実装を動かす対照テストを結びつける。
3. `just rmodel-design-write` で仕様の表示と drift 比較の入力を更新し、`just rmodel-design-check` で参照、rmodel の判定、実装の挙動を検査する。差があれば最小の再現例を残し、原因の crate で修正する。
4. `just rmodel-design-drift` で規則の文章と対応するモデルを比較する。指摘は規則とモデルのどこが食い違うかを確認して扱う。保存済みの判定は、同じモデル指定で `--replay` を渡すと再生できる。判定が欠けていれば未検査として記録する。
5. ゴールの課題を実行し、仕様の規則 ID、形式検査、drift の結果、ゴールの測定、採用判断を意思決定ログに追記する。基準や候補版を変えた場合は新しい比較として記録する。

[仕様の一覧](../../spec/rmodel-design.md)は Pkl から生成する。`just rmodel-design-check` の結果は自動検査に使い、Jev の指摘は判断の材料として扱う。

### 初回の題材は `behavior`

対照は `action`、候補は `behavior` の `guard` と `update`。主ゴールは、操作を許す条件と変更する状態を読み取れること。意味の条件は、許される操作、同時更新、代入しない変数の値が一致すること。既存テストは変数の入れ替えとロック取得の例をカバーする。意味の一致はその例の範囲で確認済み。[構文の回帰テスト](tests/behavior.rs) · [構文例](README.md)

次の比較に使う課題は、同じ入出金・ロック・セッションのモデルから、拒否される操作、更新対象、更新後の値を答えること。比較前に問いと期待値、読み手の構成、制限時間を記録する。各読み手には片方の構文だけを渡す。候補の全体の正答率が対照を上回り、どの題材でも下がらなければ改善とする。所要時間も記録する。代理読み手では `behavior` が27/27、`action` が26/27で、この基準を満たした。人の読みやすさは未測定。[0112 の評価](../../evals/iterations/0112-rmodel-readability.md)

## 検査結果と再現

`just rmodel-test` で、rmodel の参照評価器を使って判断規則を検査する。一件の変更を扱う有限モデルでは、意味の一致とゴールの改善を記録して3手で採用に到達できた。どちらかの条件を外した対照では、それぞれ2手で採用条件の違反が見つかった。採用後の改版で一方の証拠だけを残す対照も、改版後の状態との比較で検出した。矛盾した初期条件は `Empty`、予算1で探索を止めた場合は `Unknown` だった。[検査と対照](tests/calibration.rs)
