### 到達性と機能への入口

164ソースから、部品やプロジェクトの manifest が直接参照する18断片を除いた。独立モデル146件とプロジェクト9件で `rcheck coverage PATH --max-states 20000` を実行し、`--instances` 付きも別に実行した。各2秒・最大4並行で通常2件、引数付き1件が時間切れとなり、該当する3実行は個別・上限30秒で再実行した。

- 通常の探索は155入力で完了。590操作、528腕に到達した。到達不能の10腕にはすべて `expect unreachable` があった。
- 引数付きも状態探索は155入力で完了。報告された1,055組は1,021組が到達可能、34組が到達不能。138件は終了0、16件は終了1、補充モデルの1件は一覧上限で `instanceCoverage: partial`・終了3。未表示の組は件数に含めていない。[補充モデル](../../examples/model-patterns/crash-recovery/refill-queue.model)
- `behavior` は154ソース、`entity` は2、`variant` は4、`sequence` と `leads_to` は各26に現れた。低頻度の機能も、用語・値型・進行性を一緒に使う注文の実例から利用できる。出現件数は利用のしやすさや宣言の未使用を測る指標にはしていない。[注文・決済](../../examples/model-patterns/checkout/README.md)
- パッケージからアダプターごと利用できるのはブラウザ履歴、Node.js の I/O と nextTick、単一キーのオブジェクトストアの4件。今回のエラーグラフなどはリポジトリ内にモデルと実行試験があり、別の環境へつなぐには観測の変換を書く。[配布パターンの入口](../../docs/rmodel-patterns.md) · [エラーグラフの実行試験](../../tests/model-patterns/suppressed-error-graph.test.ts)
- `coverage` は操作・更新の腕・引数の診断を返す。述語内の条件や未参照の宣言は集計対象外。導出名は実装側からも観測できるため、未参照を報告するには公開型や実装が選ぶ観測名も区別する。[未参照の対照](#到達性と診断の境界) · [導出値の照合](../../docs/rmodel-patterns.md)
- 計測時、入れ子の I/O の `capabilities` は参照と明示を対応、SAT を列の変換未対応、rprob を64 atom 超過と報告した。その後、閉じた列リテラルを使うこのモデルを rprob でも検査できるようにした。自由な復旧キューにはスロット内の番号を導入した。補充モデルでは同じ番号で列を操作引数にも渡せる。再試行キューでは列の回転と、最大長を超える保存の違いを照合した。再起動モデルではチェックポイントからキューと残り試行回数を読み、順序を保ったまま残数を更新できる。適用済みバッチでは入れ子の列から集合を作って重複を判定できる。[列の符号化の判断](grammar-decisions.md#書き込める列がリテラルに限られるときだけ値域を絞る)

### 到達性と診断の境界

`examples/model-patterns` の153ソースから、部品・プロジェクトの manifest が直接参照する18断片を除き、独立モデル135件とプロジェクト9件を集計した。各入力で `rcheck coverage PATH --max-states 20000` と `--instances` 付きの実行を別々に行い、壁時計上限は各2秒とした。

- **操作と更新分岐。** 144入力すべてで全探索が完了し、563操作と436腕に到達した。到達不能の10腕はすべて `expect unreachable` と一致。通常の実行は全件終了コード0。
- **引数の組。** 到達可能959組、到達不能34組。終了コード0が127件、1が16件、3が1件。3は補充モデルの4,096組の一覧上限で、状態探索は完了し、`instanceCoverage` は `partial`。到達不能には固定の役割（ABA の C）、プロトコル上矛盾する組（未コミットと成功 XML）、現在の状態や履歴の制約（保留されなかった訪問の完了）がある。ガードを点検した範囲では、引数の宣言を狭める候補と、ガードで拒否する意味のある入力が混在している。[補充](../../examples/model-patterns/crash-recovery/refill-queue.model) · [マルチパート応答](../../examples/model-patterns/object-store/multipart-response.model) · [訪問の完了](../../examples/model-patterns/browser/navigation-activation.model)
- **式の中の条件。** 304 の `Entry` の `policy` に `if { cached.tag = requested } then Refreshed else Replacement` を置いた対照では、外側の2腕は到達可能で `branchCoverage: complete`。内側は `excluded: ["argument_instances", "embedded_value_conditionals"]` の範囲にあり、個別の位置は報告されなかった。タグが一致する `finish` の直後に `Replacement` となる条件を `witness-step` に渡すと全探索で到達不能と判定された。
- **宣言の未参照。** モデルから参照しない列挙と `derive`、初期化だけする状態変数を持つ対照では、`dead-code` と `coverage` の結果は操作 `start` の到達のみ。導出名を `validate` の `derive` で指定すると初期値 `[["Idle"]]` を取得できた。未参照の宣言を診断するなら、モデル内の参照に加え、実装の観測や公開型が使う名前も考慮する。[導出値の照合](../../docs/rmodel-patterns.md)
- **機能への入口。** `entity` は2ファイル、`variant` は4、`record` と `derive` は各16、`sequence` は19、`eventually` は3、`leads_to` は26。低頻度の機能にも実例がある。件数はパターン集内の出現数で、初見での発見率や機能の網羅率は測っていない。[用語・variant・進行性を通す注文例](../../examples/model-patterns/checkout/README.md)

### 手を入れる候補

- **検査から再生までの導線。** `Nat` を0から2まで増やす小モデルで、スコープが `0..1` のとき `witness … Scope --checker rprob` は2手で値2になる経路を返した。通常の問いの一覧には `Scope` が出ず、`--question Scope` は終了コード2。ABA の `witness` 出力をそのまま `record-itf` に渡すと、実装の各ステップの観測を含む入力形式とは異なるため終了コード2。モデルの経路、実装から記録した ITF、スコープ逸脱の経路をそれぞれどこから取得するか、同じ題材で案内したい。[再生の手順](CHEATSHEET.md#目的からコマンドを選ぶ)
- **到達性診断の粒度。** 更新式の内側にある分岐の位置と対象外の理由を出せると、手作業の `witness-step` が必要な箇所を特定できる。引数の一覧では固定の制約と状態依存の拒否を区別して読む。表に出す組数の上限と、状態探索の完了判定は独立して扱う。
- **有限値の拡大と互換性。** rprob の列は要素4種・最大長4なら空列を含めて341候補になり、型全体の64 atom 上限に当たる。まず同じ Node.js の問いで参照経路と比較できる表現を検討する。IR v1 は旧 Pkl アダプターの保存物を再生する試験があり、未知フィールド・式タグは拒否する。新しい意味を IR に追加する際は、旧入力を読めること、新入力を読めない検査器が理由を返すこと、対応する検査器で経路を再生できることを別々に検査する。分岐診断の再現には IR と別に分岐マップを保存する。[IR の互換試験](../rcheck/tests/ir.rs) · [rprob の上限](../rprob/SUPPORT.md)

配布用の `cargo package --allow-dirty --list` で、rmodel README が直接リンクするチートシート・対応範囲・設計・設計ログ・レビューの同梱を再確認した。初見の利用者が自然言語の規則からモデルを書き、検査器の対象外を見分け、実装差分までたどれるかは [バックログの手順](backlog.md#144入力の評価から進めること) で計測する。

- **対応済みで例が少ない。** `entity` は1入力、値付き `variant` は3入力、`eventually` は1入力。注文例では三つを合わせて検査できる。イベント照合の `silent` と `emit` はクエリ側で指定し、余分・欠落・値違いを検出する HTTP 試験がある。低頻度はパターン集での出現数で、利用者需要の計測とは別。[注文と決済](../../examples/model-patterns/checkout/README.md) · [通知の照合](../../tests/model-patterns/retry-threshold.test.ts)
- **観測に使う式と配布の入口。** レビュー時は `witness-step` がモデル内の `missing` を未定義として拒否した。修正後はソースと IR の両方で、不足ありの1手と解消後の5手が一致した。HTTP の公開通知でも導出名を使え、実測の導出値だけが違う故障を検出した。ITF の変換とブラウザ・Node.js・S3 型ストアの接続はリポジトリ内の例から使える。配布 API の入口は別途必要。[導出式](CHEATSHEET.md#複数の操作や性質で式を共有する) · [実装への接続](../../examples/model-patterns/README.md#自分の環境につなぐ)
- **検査器の拡張点がある。** `Checker` は対応可否と予算付きの判定を分け、JSON IR にはバージョンがある。CLI の登録は組み込みの `reference`・`explicit`・`sat`。外部の検査器を選ぶ導線は別途必要。新しい構文を低水準の式に展開できる場合は、まず IR を増やさずに試せる。新しい意味論では参照評価器と各検査器の対応範囲を合わせて検査する。[Checker](../rcheck/src/lib.rs) · [IR](../rcheck/src/ir.rs) · [対応範囲](SUPPORT.md)

### 次の試作の合格条件

1. **同じ導出式をモデルと接続側で使う。** 復旧の `missing` を DSL とクエリで、リトライの導出式を DSL・クエリ・HTTP の観測で共有した。導出式による状態変数の追加はなく、同じ性質と故障を検査できた。
2. **保存部品を二つつなぐ。** 同じ保存・配信を東西で使い、共有状態と書き込み権限を接続時に指定できた。SQLite で誤配信を検出し、権限外の代入と二重の書き込み権限を拒否した。公開操作の選択と独立した部品の型検査は次の課題。[接続例](../../examples/model-patterns/offline-merge/two-stores/README.md)
3. **固定更新のキューを一段広げる。** 4種類・長さ4のバッチを検査し、自由な初期値を持つ対照では予算によって未確定と全探索を区別した。実測では入れ子の microtask を遅らせる故障を1手で検出した。[実行試験](../../tests/model-patterns/nested-io-batch.test.ts)
4. **初見で使えるか測る。** 注文モデルを一から書き、承認の再送を検査し、HTTP の差分を再生する。完了時間と参照したページ、最初のエラーから直せるまでの時間を記録する。今回測ったのは既存例を使った再現と操作到達性。

## 利用手順と拡張性

- **検査から実装へ。** `witness` が操作列を返し、実装アダプターの `apply` と `observe` で再生すると、最初の差分と期待値・実測値が出る。保持期限の例から Rust、TypeScript、Go、MoonBit、JSON Schema も生成できた。PBT のコード生成先は現在 TypeScript と Go。接続済みのファクトリーはブラウザ履歴、Node.js の I/O と nextTick、オブジェクトストアの4つで、`examples/` のモジュールとして利用する。配布パッケージの公開 API にも欲しい場合は、モデルの同梱と rcheck への接続を含む入口を決める必要がある。[接続例](../../examples/model-patterns/README.md#自分の環境につなぐ) · [パッケージの exports](../../packages/idealis/package.json)
- **機能の見つけやすさ。** `rcheck --help` で検査、生成、照合の入口を確認できる。ITF は出荷の fixture を実装で再生する入口がある。CLI の `witness` が返す JSON から ITF へ書き出す公開コマンドは、現行のコマンド一覧にない。Lean オラクルの実行テストは4件通過した。用語・生成型・観測・証明の各入口を1題で順に試すガイドがあると見つけやすい。[CLI](../rcheck/src/main.rs) · [ITF の再生](../rcheck/tests/shipment.rs) · [Lean オラクル](../rcheck/README.md)
- **他の検査器。** 型検査後のモデル、バージョン付き JSON IR、参照評価器、独立した変換、検査器の選択が分かれているので、既存の式の範囲で検査器を追加する接続点がある。新しい型や式を加えるときは、IR の往復、参照評価、各変換の対応宣言を合わせて検査する。整数を含む保持期限の例では、参照評価器と明示探索が成立を返し、SAT の整数は対応範囲外。検査可能な範囲と各結果の `complete`・`bounded` の違いは維持したい。[検査器の登録口](../rcheck/src/lib.rs) · [IR](../rcheck/src/ir.rs) · [rprob の対応表](../rprob/SUPPORT.md)
- **SAT の宣言上限。** デコーダー廃止ではフィールド9件が ralloy の上限8件を超える。rcheck は SAT を対応外として報告し、参照評価器と明示検査器の結果はそれぞれ返す。[境界試験](../rcheck/tests/registry.rs)

- **大きさの上限。** 自由な保存キューの復旧モデルは2,728通りのチェックポイントを扱う。参照探索では状態予算4で未確定、9,000で全探索した。有限列とレコードを組み合わせた初期値も、必要な番号の候補だけ生成する。操作引数の探索でも、候補を一件ずつ生成して引数予算まで評価できる。補充モデルでは、引数を使わない先頭のガードで補充済みの状態を除き、全探索に必要な試行数を半分にした。一括の状態生成と TLA+ 変換には実体化上限が残る。証拠経路のように設定・状態・引数を指定した `validate` は、入力値の型と条件から直接検証する。[復旧モデル](../../examples/model-patterns/crash-recovery/restored-queue.model) · [実装](../idealis-semantics/src/reference.rs)
