# rmodel の文法の意思決定ログ

構文を変更するときは、実装前に、書きたいモデルの例、現行構文で困る点、比較した案と判断基準をこのログに追記する。実装後に、確認した結果と残った疑問を同じ項目に追記する。判断を見直したときは、新しい項目から以前の判断を参照する。

[設計と評価](design.md)に、変更ごとのゴールと意味の証拠を採用判断につなげる規則を記載する。

## `behavior` に `guard` と `update` を設ける

初回実装の振り返り。評価 0110 では Souther が表の構文の候補に残った。Souther の入出金モデルでは `behavior` が操作に名前を付け、`guard` が操作を許す業務ルールを示す。rmodel の `action` では条件と更新が同じブロックに並び、更新は左辺のプライムで見分ける。まず操作を許す条件と変更する状態が見分けられる構文を試した。[評価 0110](../../evals/iterations/0110-more-candidates.md) · [Souther の入出金モデル](../../evals/experiments/surface-languages/souther/bank.sou)

| 案                                                       | 判断                                                                                                             |
| -------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `behavior` を `action` の別名にする                      | 操作の名前は読みやすくなるが、条件と更新を見分ける手がかりは従来と同じ。                                         |
| `behavior` 内で `guard { … }` と `update { … }` を分ける | 採用。既存の `Action` が持つ条件と代入にそのまま対応する。複数の条件と代入も、一つずつのブロックにまとめられる。 |

`update` 自体が状態更新を示すので、左辺は `v = 式` とした。右辺はすべて遷移前の状態で評価し、代入は同時に反映する。ブロックはそれぞれ省略でき、両方ある場合は条件から先に読む順序にした。既存モデルとの互換性のため、従来の `action` を維持し、`behavior`・`guard`・`update` は宣言やブロックを読む位置でだけ構文として扱う。

**検証済み。** 変数を入れ替えるモデルで、ガードが偽になった後は遷移できず、更新されない変数が保持されることを確認した。旧構文と新構文で参照評価器の判定が一致し、Alloy と TLA+ の生成結果も一致した。README のロック取得モデルでも生成結果が一致した。[回帰テスト](tests/behavior.rs) · [ロック取得の例](README.md)

**未測定。** 条件と更新を分けることで、読み手が実際に業務ルールを見つけやすくなったかは未測定。評価 0110 の読みやすさの得点も未測定だったため、今回の採用理由は構文と既存の実行モデルの対応に置いた。

**判断の更新。** ゴールの証拠を採用判断に加えたため、この構文は評価中として扱う。対照は `action`。操作を許す条件と変更する状態を答える課題で両構文を比較する。[初回の評価課題](design.md#初回の題材は-behavior)

**仕様からの検査。** 自然言語の規則 `RMODEL-SWAP` を入れ替えモデルと構文比較テストに結びつけた。形式判定と実装検査は通過し、Jev のライブ判定と読みやすさは未測定。[0111 の記録](../../evals/iterations/0111-rmodel-spec-drift.md)

**Jev での再検査。** TypeSafe で入れ替え規則を比較したところ、矛盾 0.51 と支持 0.47 だった。同じ規則を含む対照の実行では支持 0.52 と矛盾 0.44 で、判定が割れた。参照評価器と実装テストでは仕様の動作を確認済み。読みやすさは評価中。[再実行の記録](../../evals/iterations/0111-rmodel-spec-drift.md#typesafe-api-での再実行)

**代理読み手の評価。** 入出金・ロック・セッションの三題材で rmodel の IR と14件の判定が一致した。TypeSafe の代理読み手は `action` が26/27、`behavior` が27/27。事前に定めた改善基準を満たしたが、差は一回答で人の読みやすさは未測定。この範囲の証拠を付けて `behavior` を引き続き使う。[0112 の評価](../../evals/iterations/0112-rmodel-readability.md)

## 個体を `entity` で宣言し、用語の説明を添える

実装前の判断。入出金モデルでは「口座」という用語と操作の引数の型が同じ識別子を指してほしい。自然言語の説明を別の用語表で管理する案、形式手法の語彙である `sort Account`、宣言に説明を添える `entity Account "残高を持つ口座。"` を比較した。ドメインの個体を直接表現し、同名の用語を再宣言する必要がない最後の案を採る。説明は省略できる。名前は既存の sort と同様に型・関係・scope から参照し、説明は Rust・TypeScript の型と用語集の生成に使う。

判定基準は、同じ識別子を二重宣言できず、誤記した型参照を拒否すること。旧構文と同じ意味で検査でき、IR を往復しても説明が保たれること。独立した Rust・TypeScript の実装を、入金・出金・拒否直後の状態で参照評価器に照合する。初回は rcheck の JSON Lines 契約を使う。

**検証結果。** `sig` と `entity` は参照評価器・Alloy・TLA+ で同じ意味になった。重複した宣言、未定義の型参照、空の定義を拒否し、説明は IR の往復と Rust・TypeScript の型生成で保持した。入出金では初期状態と4操作直後の JSON スナップショットが両言語で一致し、2口座の有限範囲では、各言語で到達する25状態の操作候補900件を照合し、rmodel の参照評価器と一致した。TypeScript で出金の更新を省くと、2操作の照合で不一致を検出した。[入出金モデル](../../fixtures/rcheck/bank.model) · [スナップショット列](../../fixtures/rcheck/bank.trace.json) · [規則 RMODEL-ENTITY](../../spec/rmodel-design.md#rmodel-entity)

## 到達しない操作を検出する

実装前の判断。型が正しい操作でも、初期状態からどの許される遷移を辿っても条件が成立しないことがある。単に条件式を静的に調べる案と、参照評価器が実際に到達する状態で条件を調べる案を比較し、後者を採る。検査対象は操作ごとのガードの到達可能性。全探索で成立例がなければデッド、成立例が見つかれば到達可能、探索が途中なら未確定、初期状態が存在しなければ空とする。成立した操作の更新が多重度を破った場合は、既存の `Declarations` で別に報告する。

CLI は `rcheck dead-code` とする。初期状態では条件が偽でも後から成立する操作、全く成立しない操作、矛盾した初期条件、予算切れを固定の例で区別する。Rust・TypeScript の照合はモデルが生成した操作と中間状態を対象とするため、実装の任意の分岐が未使用かは別途ソースの解析が必要。

**検証結果。** ロック解除後にだけ成立する `enter` は到達可能、条件が矛盾する `jam` はデッドと判定した。探索予算4では既に観測した `unlock` だけが到達可能で、残りは未確定。整数範囲から出る場合も、未観測の操作は未確定のまま。初期状態のない例は空と判定し、欠落のある IR は拒否した。入出金モデルの2操作はどちらも到達可能だった。[CLI テスト](../rcheck/tests/dead_code.rs) · [規則 RMODEL-DEAD-CODE](../../spec/rmodel-design.md#rmodel-dead-code)

## 別ファイルの Lean 命題を oracle として照合する

実装前の判断。rmodel の文法で命題を書く案と、Lean のファイルをコマンドで明示して既存の状態表現を渡す案を比較した。最初は後者を採る。rmodel の参照評価器で有限の到達範囲を確認した後、設定と状態の JSON の組を Lean へ渡し、各組に対する命題を `decide` で判定する。偽になったときはその設定と状態を返す。空、予算切れ、範囲逸脱、プロトコルの不正、Lean の失敗を合格にしない。命題の証明範囲は Lean 側で記述したものごとに扱い、oracle の実行結果は渡した有限の観測に限って読む。

最初の対照は入出金。rmodel の上限だけを4から5へ変え、Lean 側の上限4を固定したときに残高5の反例を検出する。正常モデルでは全観測に対して成立することを確かめる。

**検証結果。** Lean 4.35.0 で、入出金モデルの25観測に対して命題が成立した。rmodel の上限だけを5にした対照は36観測となり、残高が `Account0 = 5`、`Account1 = 0` の状態を反例として返した。空のモデルと予算切れでは Lean の起動前に終了し、出力の件数不足と Lean の型検査エラーはエラーとして扱った。例の定理 `zeroInRange` は追加の公理に依存しない。[実行手順](../rcheck/README.md#lean-snapshot-oracle) · [Lean の定義](../../formal/rmodel/Bank.lean) · [oracle の CLI テスト](../rcheck/tests/lean_oracle.rs)

## 分割した仕様から業務ルール・選挙・境界テストを記述する

一つのファイルで用語の宣言と振る舞いを混在させる案、DSL に `import` を加える案、外側に順序付きのマニフェストを置く案を比較した。最初にマニフェストを試す。名前空間とスコープは一つに保ち、型の参照・重複と操作の意味は既存の rmodel で検査できる。ファイル単位の名前空間、依存関係、構文エラーの原本位置は今後の設計に残す。

出金の金額は既存の `record` で表し、業務上の最終結果は `enum` の値として状態に持つ。要求が受け付けられたかはガード、残高不足で確定したかは結果に対応する。値の制約は既存のガードに書く。将来、型自体に制約を持たせる案を比較するときは、生成先の型と境界テストに同じ制約を渡せるかを判断基準にする。

境界は比較式の形と、到達する状態での判定の差から導く二案を比較した。後者を試す。出金の整数だけでなく、Raft で票を一つ追加したときの変化も同じガードの判定で測れる。隣接整数を受け付けた後に確定操作の受付が分かれるときも境界にする。設定・操作・種類ごとに最初の組を採り、先行操作、受付の真偽、直後の状態を付ける。判定条件と実測は [計画](../../evals/plans/0113-linked-boundaries.md) と [結果](../../evals/iterations/0113-linked-boundaries.md) に記録した。この構成は試作として扱う。

**Go への展開。** Go では既存の型生成が出すモデル固有の interface を再利用し、生成テストへは型付きの factory を渡す。設定・コマンドは再生の入口でデコードする。TypeScript も生成プロパティがデコードの戻り値を factory に渡す形にそろえた。出金の両テストは同じ境界コーパスを使う。[使い方](../rcheck/README.md#generated-go-interface-and-fuzz-test)

## Nat と演算範囲を区別する

Nat のために独立した有限範囲を宣言する案と、同じ整数スコープの非負部分を使う案を比べ、後者を試す。型名で金額や個数の符号を宣言でき、Int と Nat の比較は整数として共通に読める。引き算は正負を含む整数演算で、自然数の変数やフィールドへ格納するときに結果の範囲を確認する。これにより、残高不足をガードに書いた場合と、ガードの書き忘れで負の残高を作る場合を区別する。

列挙範囲と、数値表現の限界は別に検査する。参照評価器では符号付き64ビットの正確な計算を使い、TLC 向けには別の上限を適用する。式の範囲はガードに依存せず保守的に見積もる。実装を呼ぶ前の検証では型だけでなく設定・初期状態・ガード・遷移先を確認する。[計画](../../evals/plans/0115-nat-validation.md)

## 有限列と値付き variant を値にする

ログを位置と二項関係に手で展開する案と、順序を持つ値として宣言する案を比較し、後者を実装した。順序と重複は型、IR、観測に引き継ぐ。長さは宣言で制限し、添字は0始まり。範囲外の読み取りは空で、追加後に上限を超えて格納すると Scope で観測する。JSON では `$sequence` を使って集合の正規化と区別する。

variant はタグに対応する一つの値を持ち、複数項目は record にまとめる。値のないケースも宣言できる。Pkl の注文モデルからタグ・ペイロード・条件を IR に写し、二状態の性質は `omitted` に残す。

## 進行性と公平性を問いごとに指定する

到達可能性に公平性を暗黙に加える案と、時相の問いで仮定を明示する案を比較し、後者を実装した。`eventually` はいつか成り立つことを要求し、`leads_to` は前件を満たすたびに応答を要求する。既定の弱／強公平性を問い単位で上書きできる。引数を持つ操作の公平性は、引数のいずれかで実行された操作全体にかかる。永遠に待つ配信と、一時的に接続できる配信で公平性の差を測った。[評価 0116](../../evals/iterations/0116-structured-temporal.md)

## 遷移の直前と直後を一つの式で読む

前の式と後の式を別々のブロックにする案、プライムで後状態を示す案、式を `before(...)` と `after(...)` で包む案を比較した。前後の任意の式を同じ比較や条件に置けるよう、最後の案を試す。読み比べの対照にはプライムを使い、型検査後は同じ IR に正規化する。

`transition` は実行可能な操作の前後にかかる。操作が状態を変えない場合でも検査する。rmodel の明示的な操作と暗黙の待機を TLA+ で区別するため、実行した操作の後に内部のビットを反転させる。公平性は進行性の問いにかかり、遷移の検査はすべての有効な操作を対象にする。

出荷と再試行を二人の代理読み手が読み、どちらの表記も6問中6問正解した。差が出なかったため、明示表記は試作のままとする。[評価 0117](../../evals/iterations/0117-transition-readability.md)

発送の仕様から `ShippedStays` を参照するときは rspec の既存の要件 ID と claim を使う。同じ操作列を各言語で比べるため、期待状態は rmodel の参照評価器から ITF に取り出し、生成したインターフェースを実装した各言語の観測と照合する。要件 ID とトレース形式は既存の仕様とテストの層に置く。[評価 0118](../../evals/iterations/0118-shipment-drift-and-replay.md)

## 自然文の節に遷移の検査とレビューを結ぶ

要件全体の参照だけ、要件全体の版を持つ、節ごとに式と版を持つ、の三案を発送で比較した。式が成立しても追跡方法の節が式から消える例があり、節の参照があればどこが未検査かを表示できる。モデルの振る舞いが変わった場合は検査結果を失効させ、自然文と式の対応レビューは対象の組で判定する。確認操作のガードを強める修正は、追跡方法の維持を成立させても、配送方法ごとの確認済み状態への到達を失う場合があった。節ごとの形は試作として扱う。[評価 0119](../../evals/iterations/0119-requirement-links.md)

0120 では節ごとの版を rspec 側に置いた。節は rmodel の名前付きの検査を参照し、CLI は現在のモデル判定と対応レビューの版を出す。発送の確認操作を残すために、状態を維持する性質と配送方法ごとの到達を別の検査にした。 [評価 0120](../../evals/iterations/0120-reviewed-clauses.md)
